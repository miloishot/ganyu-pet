# ganyu-pet — Contracts & Spec

Desktop pet overlay: Ganyu (from the installed Codex pet `ganyu--chenxin-dlut`) lives on the Windows desktop, reacts to codex CLI **and** Claude Code lifecycle-hook events, chats in character via Haiku, and wanders the bottom edge of the screen whenever nothing needs the owner's attention.

This file is the single source of truth for parallel builders. **Own only your files. Interfaces here are binding.**

Voice unit tests, with a fake WebSocket and no network and no child process: the `Sec-MS-GEC` token is deterministic for a fixed clock and floors to five minutes (and still matches the standalone probe that was verified live, byte for byte); a 403 surfaces as a **named** `VoiceAuthError` whose message names both the constant to change and its current value, and **falls back** rather than throwing; a socket that never opens times out and returns null; one that opens and never answers times out, is dropped, and does not wedge the line after it; the warm socket is reused across two speaks and a closed one reconnects; a newer line supersedes the one being synthesized and the superseded one stays silent *including through the fallback*; late audio for an abandoned request is never spliced onto the next line; `close()` settles a line in flight. On the gate: a line and its audio reach the renderer in the same message, and a muted, throttled or non-salient line makes no sound at all — including one muted *while it was being synthesized*. On the hold: the deadline is exactly `AUDIO_HOLD_MS` and expiring it shows the line unvoiced rather than leaving her silent and invisible; audio arriving after it is played late rather than discarded; a synthesizer that *fails* shows the line at once rather than at the deadline; a held line still blocks the next one through the throttle; a muted pet is quiet but not slow; an urgent kind is never held and is voiced late instead; a second line cannot overtake the first out of order, a superseded line is never shown behind the one that replaced it and its deadline cannot fire afterwards, and `dispose()` lets go of whatever was waiting. On the chat seam: a reply comes back as `{text, audio}`, and a reply whose voice failed, threw, rejected or was never wired is still a reply. On the config: no `.env.local` at all still has a voice, `GANYU_VOICE` turns her off or pins her local, and a key he never wrote is not a key he turned off. On the fallback: `powershell.exe` (never `pwsh`) with an `-EncodedCommand` one-line `System.Speech` script whose quotes are doubled rather than escaped. On the renderer: a new line interrupts the one playing, only the two known mimes are ever pasted into a `src`, an overlay with no `<audio>` element is a silent pet rather than a broken one, a line arriving with its audio is shown and played in the same tick, audio for a line the bubble *refused* is never heard, late audio for a line already up is played on arrival, and the pending dots come down onto the reply and its sound together.

## Runtime architecture

Electron main process runs: HTTP hook server (module B) → state aggregator (B) → pushes to renderer via IPC (A) → renderer animates sprite + bubbles (C). Speech (D) and wander (E) are main-process modules driven by state transitions, with injected dependencies so they unit-test without Electron.

### HTTP contract (module B)

- `POST /event/:source` where `:source` ∈ `codex|claude|opencode`. Body: the raw hook JSON (may arrive URL-encoded as `payload=<json>` form data — accept both raw JSON body and `application/x-www-form-urlencoded` with a `payload` field, mirroring how Orca's hook forwards stdin).
- `GET /state` → `{ mode, sessionCount, sessions: [{id, source, mode, lastSeen}], celebrate: bool, wandering: bool }`.
- `GET /healthz` → 200 `ok`.
- Port **47821** (env `GANYU_PORT` overrides). Bind `127.0.0.1` only. If the port is taken: log a clear error and exit 1 (hook scripts hardcode the port).
- Server must be constructable standalone (`node src/main/server.mjs --standalone [--port N]`) with no Electron import.

### Event normalization & state machine (module B)

Payloads differ between codex and Claude Code — normalize defensively:

- `sessionId`: `payload.session_id ?? payload.thread_id ?? payload.sessionId ?? "<source>-unknown"`.
- `event`: `payload.hook_event_name ?? payload.event ?? payload.type ?? ":source-path-hint"` (the hook script also passes the event name when it can't be parsed; unknown events → activity ping only).
- Claude Code sample (real shape): `{"session_id":"abc","transcript_path":"...","cwd":"C:\\...","hook_event_name":"PreToolUse","tool_name":"Bash","tool_input":{...}}`. Codex payloads: assume similar keys, parse tolerantly, keep the raw payload in a debug ring buffer (last 50, exposed at `GET /debug/events`, loopback only).

Per-session mode from last event:
`PreToolUse|PostToolUse|UserPromptSubmit|SubagentStart|SubagentStop|SessionStart` → `busy` · `PermissionRequest` (codex) / `Notification` (Claude, permission-flavored) → `waiting` · `Stop|SessionEnd` → `idle` (Stop also sets `celebrate` for 10s) · payload with `error|failed` markers (case-insensitive scan of tool_response/last message) → `failed` (sticky 30s, then falls back to the underlying mode).

Aggregate mode = highest priority across live sessions: `failed > waiting > busy > idle`. Sessions expire after 10 min without events (sweep interval implementation-defined — currently 1s; TTLs unchanged). `celebrate` is a transient flag alongside the mode, not a mode.

State module exposes `createState({clock})` returning `{ingest(source, payload), aggregate(), onChange(cb)}` — injectable clock (`clock.now()`) for tests; production passes `() => Date.now()`.

### IPC contract (A ↔ C, via preload `window.ganyu`)

Preload exposes exactly:
- `ganyu.onState(cb)` — cb receives `{mode, sessionCount, celebrate, walk: {dir: 'left'|'right'} | null, dragging, airborne}`.
- `ganyu.onSpeak(cb)` — cb receives `{text, audio?}`, where `audio` is `{mime, base64}`. **The line and the sound of it arrive together** whenever synthesis finished before main gave up waiting for it (`AUDIO_HOLD_MS`, see §Voice); the renderer shows and plays them in the same tick. `audio` absent means unvoiced *so far*, not never: see `onAudio`. The renderer plays bundled audio **only if the bubble accepted the line** — a hook line refused because a reply still holds the bubble must not be heard, since he will never see it.
- `ganyu.onAudio(cb)` — cb receives `{mime, base64}` for a line **already on screen**. This channel used to carry every line's audio, which is what put her voice one to four seconds behind her own bubble; it now carries only the two cases where the words could not wait — an urgent kind (`waiting`/`failed`), and any line whose synthesis overran the hold. Main sends it only for lines that already passed the mute and salience gates, so the renderer has nothing left to decide beyond interrupting whatever she was mid-sentence on.
- `ganyu.setInteractive(bool)` — toggles `setIgnoreMouseEvents(!bool, {forward: true})`.
- `ganyu.menuAction(action)` — `'toggle-mute' | 'toggle-pin' | 'home' | 'quit'`. `home` is the recall action (see §Window); main filters against `MENU_ACTIONS`, so anything else is dropped.
- `ganyu.drag(phase)` — `'press' | 'release'`: the left button went down on the sprite, or came up. Only the button — whether that press *is* a drag is main's call (see §Drag), and comes back as `dragging` on `ganyu:state`. Filtered against `DRAG_PHASES` exactly as the menu action is.
- `ganyu.getFlags()` → Promise of `{muted, pinned, spritePath}` (spritePath as `file://` URL for the `<img>`/canvas source).
- `ganyu.sendChat(text)` → Promise of `{text, audio}` — her reply and, when synthesis beat the hold, the sound of it — or `null` when there is no reply at all. Never rejects, and never outlives the hold: the pending dots cover both the brain writing the line and the synthesizer voicing it, so the reply and its audio come down onto the bubble together (see §Chat, §Voice). The renderer still accepts a bare string, which is what this channel answered before she had a voice.
- `ganyu.setFocused(bool)` — lifts and restores window focusability so the chat input can take a keystroke (see §Window).
- `ganyu.setOverlayOpen({menu})` — what the overlay currently has open. Sent on **every** menu open and **every** close path there is, because it is what arms and releases the global Escape hook (see §Dismissing the menu). Coerced to a plain boolean in main: two things hang off this flag and neither may be armed by a truthy accident.
- `ganyu.onDismiss(cb)` — cb receives `'escape' | 'pointer-left'`, the two dismissals main owns on the overlay's behalf. Filtered against `DISMISS_REASONS` in the renderer exactly as menu actions and drag phases are filtered in main.

Channels (main side): `ganyu:state`, `ganyu:speak`, `ganyu:audio`, `ganyu:dismiss`, `ganyu:set-interactive`, `ganyu:menu`, `ganyu:drag`, `ganyu:overlay-open`, `ganyu:get-flags`, `ganyu:chat`, `ganyu:set-focus`. Nothing else.

The nine main-owned names are in `window.CHANNELS`; the chat pair is named in `chat.CHAT_CHANNELS` and **not** duplicated into `CHANNELS`, because two frozen tables of the same strings is the only way they could drift. `window.registerIpc` registers and disposes the renderer→main half; `state`, `speak`, `audio` and `dismiss` are push-only and have nothing to register. The preload hardcodes every string, as it always has — it is CommonJS and cannot import an ESM module.

**`dragging` and `airborne` ride `ganyu:state` rather than getting channels of their own.** The renderer wants them for the same reasons it already wants `walk` — to choose a sprite row, and to know whether the pointer is doing something to her — and one deduped push is cheaper than three. `toStatePayload(aggregate, walk, motion)` assembles them; both default to false, so a caller that knows nothing about motion produces the original payload plus two falses. They are **not** the same flag: `dragging` ends at the mouseup, `airborne` stays true through the whole throw until she lands.

### Window (module A)

Frameless, transparent, `alwaysOnTop: 'screen-saver'`, `skipTaskbar`, not resizable, ~256×320 (192×208 sprite + bubble headroom), initial position bottom-right of primary display `workArea`, `webPreferences: {contextIsolation: true, preload: preload.cjs}`. Default click-through ON via `setIgnoreMouseEvents(true, {forward: true})`; renderer flips interactivity on sprite hover (see C). `GANYU_SMOKE=1` → after ~5s print `SMOKE_OK ` + JSON `{transparent, alwaysOnTop, frame:false}` to stdout and `app.quit()`. Single-instance lock. Wires modules together: server → state → (renderer push, speech, wander).

**Measured size, not `WINDOW_SIZE` — and measured exactly once.** Two facts about this machine (Electron 43.2.0 / Windows 11 22000, primary display `workArea` 1707×1019, `scaleFactor` 1.5), both measured live:

1. Windows adds invisible frame padding even to a frameless transparent window: a 256×320 request measures **259×323**. Clamping the pet against `WINDOW_SIZE` therefore left her right and bottom edges ~3px outside the work area.
2. **`win.getBounds()` is not a stable size.** Every `setPosition` inflates the reported width and height by ~1px — 259×323 at create, 458×523 after 200 moves — and `setSize(256, 320)` does not reset it. It is a DIP↔physical round-tripping artifact of the 1.5 scale factor.

So module A captures the size **once, before anything calls `setPosition`**, caches it, and hands that to everything that needs geometry: wander's `getWindowSize`, `computeInitialBounds` for the recall target, and the hover watch's bounds (live position + stable size — the inflating size slid the sprite's hover box off the sprite the longer she walked, until the right-click menu could not be opened). Re-reading the size live walks the pet up the screen ~1px per tick; do not "fix" it back into a live read. Production values: **maxX 1448, floor 696**.

**Containment.** Module A calls `wander.containNow()` (a) once on startup, right after the window exists — the initial `computeInitialBounds` placement is derived from `WINDOW_SIZE` and is already ~3px outside; (b) from the existing 1s state poll, which is cheap because module E no-ops when she is already inside; and (c) on the `screen` events `display-metrics-changed`, `display-added` and `display-removed`. Listeners are removed in `cleanup()`.

**Recall.** `MENU_ACTIONS` is `['toggle-mute', 'toggle-pin', 'home', 'quit']`, and the menu entry for `home` is labelled **Come here**. It is the last resort for a pet the owner cannot reach, and works while pinned and while the aggregate mode is stuck non-calm.

`home` places her at `computeInitialBounds(workArea, measuredSize)` **through module E's hold API** — `grab()`, `moveTo(x, y)`, `release({vx: 0, vy: 0})` — not by moving the window itself. It used to `cancel()` the stroll and then `moveWindowPinned` directly, which was correct only while falls were rare: `cancel()` deliberately leaves a fall running (§Wander), so once throws existed, a recall mid-flight was undone one tick later by physics still integrating from where she used to be. `grab` drops the stroll *and* the fall, `moveTo` writes the position through the single writer, and `release` hands her back to the ordinary scheduler. The old path survives as the fallback for a module E that has no `grab`.

**Focus, and why the chat input needs it lifted.** The window is constructed **`focusable: false`** — an always-on-top overlay must never take the caret out of the editor — and a window that cannot be focused cannot deliver a keystroke to its own text input either. `ganyu:set-focus` is the lever: `true` → `setFocusable(true)` then `focus()`; `false` → `setFocusable(false)` then `blur()`. The order matters in both directions. Focusing before lifting the flag is a no-op, and dropping the flag without blurring leaves the window holding the focus it already had, so the caret never goes back to what he was typing in. The renderer asks on open and gives it back on close. A missing, destroyed or uncooperative window is swallowed: a chat strip he has to click twice is annoying, and never a reason to take the pet down.

### Renderer (module C)

Canvas-based sprite engine. Spritesheet grid — 8 columns × 9 rows, frame 192×208, row map:

| Row | Animation |
|---|---|
| 0 idle · 1 run-right · 2 run-left · 3 waving · 4 jumping · 5 failed · 6 waiting · 7 busy run-in-place (**unmapped**) · 8 review (standing working pose) |

**Frames per row are not uniform.** The grid is 8 wide but only rows 1, 2 and 5 fill it; the rest end early and their trailing cells are fully transparent. Measured opaque-pixel counts (`ROW_FRAMES` in `pet.mjs`):

| Row | 0 idle | 1 run-right | 2 run-left | 3 waving | 4 jumping | 5 failed | 6 waiting | 7 busy | 8 review |
|---|---|---|---|---|---|---|---|---|---|
| Frames | 6 | 8 | 8 | 4 | 5 | 8 | 6 | 6 | 6 |

Mode → row: `idle→0`, `busy→8`, `waiting→6`, `failed→5`, `celebrate` pulse → 4 (jump) then 3 (wave) once, `walk.dir right→1 / left→2`. 8 fps default, 6 fps for walk rows.

**`airborne→4` (jump), and it outranks both.** Held in the cursor or mid-throw, she is plainly not standing on anything, so neither the walk rows nor the mode row can be right. Row 4 is the only pose on the sheet that is not a stance, and it covers being carried and being thrown alike — from the sprite's point of view those are the same situation. Its 5 real frames make it the one row whose `ROW_FRAMES` entry has always mattered.

**Row 7 is intentionally unmapped.** It is a run-in-place animation, so playing it while the pet is stationary reads as running on the spot without moving. Stationary `busy` therefore draws row 8 (review), a standing thinking pose; real locomotion already draws rows 1/2 via `walk.dir`, which outranks the mode. The row stays in `ROW`/`ROW_FRAMES` because it still exists on the sheet — it is simply unreachable from any mode. Loop each row's real frame count, never the full 8 — drawing a blank trailing cell blinks the pet out (idle at 8 fps lost 250ms of every second). Chromium decodes `.webp` natively — draw via offscreen `<img>` → `drawImage` crops.

Hover behavior: `mouseenter` on the sprite's bounding box → `ganyu.setInteractive(true)`; `mouseleave` → `false`. Right-click on sprite → minimal in-window menu (Mute/Unmute · Pin/Unpin · **Come here** · Quit) → `ganyu.menuAction(...)`. Speech bubble: styled div above the sprite, fades after 8s, newest replaces current.

**The pending state is wordless.** While a reply is in flight the bubble shows `THINKING_MARK` (`•••`) under the `is-thinking` class, pulsed by a CSS `color` animation — not a sentence. It used to say *"Let me think for a moment…"*, and the trouble with that is not the sentence but its frequency: it is the same words before every answer she ever gives, which reads as filler and as stalling rather than as thought. Dots say the only thing that needs saying, which is that she heard him and something is happening. `CHAT_FAILED_LINE` stays a sentence, because it is rare and has something to say.

Three details are load-bearing. It is still **text in the same bubble**, so §Chat's priority arbitration needs no changes — a pending exchange holds the bubble against ambient lines exactly as the sentence did, and the reply replaces it simply by being the newer chat line. The class is cleared inside `bubbles.put()`, so **anything shown next takes the dots down** — the reply, the failure line, teardown, or an ambient line that gets in after the 8s hold lapses — rather than three call sites having to remember. And the pulse is on `color`, never `opacity`: fading the element fades the panel, border and shadow with it, and a breathing speech bubble reads as a rendering fault. `prefers-reduced-motion` drops the animation and keeps the dots.

**Every `MENU_ACTIONS` entry needs a `menuLabels()` entry.** `paintMenu` writes only labels it finds, so a missing one is a silently blank button rather than a crash — which is exactly how `home` stayed unreachable for two modules' worth of work while main filtered it through faithfully. `test/renderer.test.mjs` walks the action list against the label table for that reason.

**Interactivity latches.** `createInteractivity` ORs five: `overPet`, `overMenu`, `menuOpen`, `chatOpen`, `dragging`. The last exists because the window chases the cursor during a drag, so on a fast throw it trails behind and the pointer spends most of the gesture off the sprite — without the latch the overlay would go click-through mid-throw and the `mouseup` that ends the drag would land on the desktop. `releaseAll()` drops all five, and in the renderer it is only ever reached through a wrapper that closes the menu and the input strip first — see the invariant below.

### Dismissing the menu

**`focusable: false` silently deletes two of the menu's three exits, and that is what made the pet unusable.** The window is built unfocusable so an always-on-top pet can never take the caret from the editor (§Window), and that flag must stay. What nobody wrote down is its consequence for input: a window that never takes focus receives **no key events**, so the renderer's `keydown` handler cannot see Escape; and a window that cannot be focused cannot be **blurred**, so its `blur` handler never fires either. Both of the menu's keyboard-shaped exits were dead from the day they were written. The chat strip is exempt only because `openChat` lifts focusability first — that lift is precisely what makes its Escape and blur real.

A third exit was dead for an unrelated reason. On Windows the right button fires `mousedown` **before** `contextmenu`, and the document-level mousedown handler closed the menu on that mousedown — so `canvas.contextmenu` then found it hidden and opened it straight back up. Right-clicking her to dismiss the menu only moved it, and the `else closeMenu()` branch could never run. The renderer's fake DOM does not bubble, which is why the toggle test passed against a toggle that could not work; the replacement test dispatches the document mousedown explicitly.

**Five ways out, and no single one of them is load-bearing:**

| Route | Owner | Note |
|---|---|---|
| Click a menu entry | renderer | acts, then closes |
| Right-click anywhere on the menu | renderer | a toggle is what a right-click implies; this used to `preventDefault()` and stop |
| Right-click or left-click the sprite | renderer | the sprite is exempt from the document mousedown rule, so the canvas handlers own the whole gesture. A click that dismisses the menu is **spent**: it does not also open the chat strip |
| Escape | **main** | `createEscapeHatch` — a `globalShortcut` registered on menu open and unregistered on close |
| Pointer left the window for `MENU_LEAVE_GRACE_MS` | **main** | `createLeaveWatch`, on the existing hover poll |

**The Escape hook is a loan, not a fixture.** While registered it takes Escape from the whole machine, so it is armed only between the menu opening and the menu closing, and released by: the renderer reporting the close (every close path calls `setOverlayOpen({menu:false})`), the pointer-leave grace expiring, the renderer reloading (`did-finish-load`), the renderer dying (`render-process-gone`), the window closing, and `will-quit` → `cleanup()`. It also **releases itself the instant it fires**, before the renderer is told anything — a wedged renderer must not be able to keep Escape. A failed `unregister` still clears the armed flag, because believing we are armed would make the next `arm()` a no-op, and *that* is how a stale hook would outlive its menu. Registration returning false (another app owns Escape) is a warning, not a failure: the other four routes stand.

**`MENU_LEAVE_GRACE_MS` is 1200** — ten samples at `HOVER_POLL_MS`, so a single stray cursor reading cannot trip it. Travelling between the sprite and the menu cannot start the clock **at all**, because both live inside the same 256×320 window and the cursor never leaves it on that journey; the guarantee is structural, not a generous timeout. A cursor or bounds reading that could not be taken counts as *inside* — an unknown is not evidence he walked away. Read from the cursor poll rather than a renderer `mouseleave`, for the reason `createHoverWatch` already documents.

**The invariant: the menu may never outlive the latch that makes it reachable.** A visible menu on a click-through window is painted, unclickable, un-hoverable, and has no event left that could ever close it — the exact state that costs a restart. `guardMenuReachable()` closes it instead, and runs on the frame loop and on every `ganyu:state` push (two carriers because neither is sufficient alone: the frame loop does not exist when the spritesheet failed to load, and state pushes are deduped).

**The input strip is deliberately not covered by that guard, and the asymmetry is the point.** `setIgnoreMouseEvents` takes the mouse and leaves keyboard focus alone, so a menu on an unlatched window is unusable while an input strip on one is merely unclickable — he can still type into it and still press Escape. Force-closing it would destroy a half-written message to fix nothing. For the same reason `'pointer-left'` never touches the strip (he walks the cursor off a 256px window constantly while typing), and `'escape'` is layered: with a menu up it takes the menu and leaves the message alone.

### Drag (module A — `createDragTracker` in `window.mjs`)

Pick her up with the left button, carry her, let go, and the physics in §Wander throws her. Pure and injected exactly like `createHoverWatch` next to it: `{now, getCursorPoint, getPosition, grab, moveTo, release, onDragging}` → `{press(), poll(), release(), cancel(), dragging, pressed}`. It never touches the window — `grab`/`moveTo`/`release` are module E's API, and **two writers of the window position is the bug this shape exists to prevent**.

**Why the renderer only reports the button.** The obvious design — mousedown/mousemove/mouseup in `pet.mjs` — fails twice on this machine. First, forwarded mouse-move does not reliably reach a click-through always-on-top window (measured: 1 of 9 trials; the same finding that forced `createHoverWatch`), so a drag that needs mousemove works only sometimes. Second, and independent of that: the window follows the cursor, so client coordinates barely change while she moves, and a renderer drag reads its own output back as input. So the renderer sends `press` and `release` and nothing else, and everything between them is read from `screen.getCursorScreenPoint()` on a `DRAG_POLL_MS` (**16ms**) interval that exists only between those two messages.

**Click vs drag** — `shouldPromoteDrag({from, to, elapsedMs})`, exported and pure. A press becomes a pick-up when the cursor has moved further than `DRAG_THRESHOLD_PX` (**4**, straight-line distance, so diagonal jitter counts once) **or** it has been held `DRAG_HOLD_MS` (**250ms**). Both are needed. The distance rule is what makes a flick feel immediate; the *time* rule is the one that carries this machine, because it needs no mouse events at all — and on an overlay that may never deliver a mousemove, a distance-only rule would silently turn every drag into a click. A left click opens the chat strip, so the cost of getting this wrong runs in both directions: a pet that jumps when he meant to talk to her, or an input strip that opens when he meant to move her. 4px is comfortably above the hand jitter of a deliberate click; 250ms is roughly twice a deliberate click and well under a considered one.

**The throw** — `throwVelocity(samples, now, windowMs)`, exported and pure. She follows the cursor exactly while held, so the cursor's velocity at the moment of release *is* hers. Only samples fresher than `THROW_SAMPLE_WINDOW_MS` (**100ms**) count, and fewer than two fresh ones is zero rather than a guess. Dropping the stale ones is the whole point: a drag that crosses the screen and then pauses before letting go has to read as a set-down, and averaging over the whole gesture is exactly how it would instead read as a throw at the speed it was travelling a second ago.

**Anchoring.** The offset between window and cursor is fixed at the moment of the pick-up, from the *press* point (`window position at grab − cursor at press`), so she moves by the whole gesture rather than snapping into the pointer, and a stroll that carried her somewhere else between the press and the promotion is accounted for.

**Backstop.** `DRAG_MAX_MS` (**30s**) ends a drag that never got its `release`. The release comes from a renderer `mouseup` on a window being moved under the cursor 60 times a second; if one ever goes missing she is stuck to the cursor until the app restarts, which is a worse failure than dropping a genuinely long hold. `cancel()` is the teardown path and puts her down where she is rather than throwing her.

**Renderer side.** `pet.mjs` holds three flags: `pressing` (left button down on the sprite), `dragging` (main promoted it, learned from `ganyu:state`), and `suppressClick`. The last is load-bearing: a drag ends in a `mouseup` on the sprite, which is also the second half of a `click`, so without it letting go of her would open the chat strip every single time. It is set locally on mouseup rather than waiting for main to confirm — `click` fires immediately after `mouseup`, long before an IPC round trip could come back — and cleared by the click it swallows or by the next press, so exactly one click is ever eaten. `mouseup` is bound on the **document**, not the canvas, because a fast drag leaves the window trailing the cursor. A `blur` and `dispose()` both end an outstanding press, so she is never left stuck to a cursor the window will not hear from again.

### Speech (module D)

`createSpeech({exec, clock, onLine, isMuted})` — `exec` injected (production: `child_process.execFile` of `C:\Users\kw11l\.local\bin\claude` with args `['-p', prompt, '--model', 'haiku']`, 60s timeout, kill on expiry — measured CLI latency on this machine is 23–57s, so 15s starved every live call).

- **Triggers**: `SessionStart` (greeting), `Stop`/`SessionEnd` (celebrate), `waiting` (nudge), `failed` (sympathy), the first successful **completion** after a failure (**recovered**), and a tool-class change during `busy` (busy). Queue depth 1 — a newer trigger replaces a pending one.

  **A recovery is a completion, never a `PreToolUse`.** During a retry loop "about to run it again" is the commonest event of all and says nothing about whether the trouble cleared; counting it as a recovery would reset the failure streak on every attempt and hand her a fresh sympathetic line each time — the exact defect the streak rule exists to prevent. Only `PostToolUse`/`Stop`/`SessionEnd` without an error marker (`succeeded(ev)`) clears the streak or fires `recovered`.

- **Salience — the gate that decides whether a trigger is worth a line at all.** `salienceOf({kind, failStreak, quietForMs, sinceNotableMs, patterns})` (exported from `speech.mjs`, pure) returns `{level, reason}` with `level` ∈ `urgent | always | notable | null`. It lives in speech rather than context because it is a decision about *speaking*, and `context.mjs` is deliberately stateless with no notion of what the pet has said.

  | Level | When | Throttle |
  |---|---|---|
  | `urgent` | `waiting`; `failed` at streak 1, 3, 5, then every 5th | 0 — except `THROTTLE_MS` (**6s**) against another line of the **same** kind, so seven sessions hitting one wall is one bubble |
  | `always` | `greeting`, `celebrate`, `recovered`, or her first line after `QUIET_STRETCH_MS` (**10 min**) of silence | `QUIET_THROTTLE_MS` (**90s**) |
  | `notable` | a pattern fired **and** none has been remarked on for `NOTABLE_INTERVAL_MS` (**10 min**) | `QUIET_THROTTLE_MS` |
  | `null` | everything else — routine `PreToolUse`/`PostToolUse` for Read, Grep, Glob, Edit, Write, Bash and friends | never spoken (`reason: 'not-salient'`) |

  Patterns are tallied in speech's own 20-minute trail (one small record per event — not a second copy of `summarizeRecent`, which reads a ring speech cannot see and is one event behind): the same file touched **5+** times, the same command run **3+** times, **4+** distinct sessions seen, or **25** consecutive events in one project.

  **Why this exists.** The old rule was a flat 6s throttle and a line on *any* trigger, so with several agents streaming lifecycle hooks she narrated whichever Read happened to clear the gate — "she keeps telling me the most random things". Repeated failures were the same defect in miniature: every retry got its own sympathetic line until sympathy read as nagging. Silence is what makes the remaining lines mean anything, which is why the non-urgent cost of a line went up 15x rather than the trigger list getting shorter.

- Persona prompt: `BRAIN_INSTRUCTIONS` in `persona.mjs` — see §Brain.
  `OWNER_NAME` is **Kahweng** (owner's preferred name — no honorific, never "Mr.").
  `{summary}` = compact human phrase built from the normalized event (`"codex finished a task in ganyu-pet"`, `"Claude Code is waiting for permission to run Bash"`).
- On exec error/timeout/empty output → canned fallback from the `MESSAGES` table in `persona.mjs`, same cooldown rules. Muted → no exec calls at all. Six kinds — `greeting`, `busy`, `waiting`, `failed`, `recovered`, `celebrate` — 3–5 variants each, ≤ `MAX_LINE_CHARS` (70), at most one emoji, no honorific, and at least one slot-free variant per kind so an event with no tool or project still renders. `recovered` is its own kind rather than a `busy` line because "Running Bash…" is the wrong thing to say at the moment the trouble clears, and because the brain writes a better line when it is told which of the two moments this is.
- **Memory** — `createSpeech({…, ledger})` takes an optional `{record(entry)}`; absent (the default) is the original behaviour, in which she reacts and forgets. Speech is the ledger's only writer, and what it writes is a translation of the salience decision above, never a second opinion on it. See §Ledger for the placement (after salience, before the throttle, after mute) and for why `busy` is never recorded.

### Brain (optional LLM speech — module D)

`src/main/brain.mjs`: `createBrain({config, fetchImpl, now, log, timeoutMs, toolTimeoutMs, getContext, getMemory, searchMemory, readSession})` → `{requestLine({detail, summary}), requestChat({text, history}), isEnabled(), stats()}`. Module A loads the config, constructs it when enabled, and hands it to `createSpeech({…, brain})` **and** to `createChat({brain})`. **Optional in every sense** — with no config, or a config that stops working, the deterministic MESSAGES path above behaves exactly as it does today, synchronously, and chat answers null. Global `fetch` only; no dependencies.

**Two request kinds, one transport.** `requestLine` is the ambient path (a hook event became a briefing, she remarks on it); `requestChat` is the reply to something the owner typed. Route order, the remembered route, the 404/405 fallback, the 401/403 kill switch, `store:false`, the reasoning effort and the 10s timeout are written once and shared, so they cannot drift apart. What differs is only the prompt, the length allowed, and the latch.

- **Config** — `<repo>/.env.local` (git-ignored; read here and nowhere else), parsed as plain `KEY=VALUE` with blank lines and `#` comments skipped. Required keys: `GANYU_OPENAI_BASE_URL`, `GANYU_OPENAI_MODEL`, `GANYU_OPENAI_API_KEY`. A missing file or any missing/empty **required** key → `{enabled:false, reason}`, and the brain is never constructed. Five optional keys, none of them required and each with a default that stands when the key is absent: `GANYU_OPENAI_REASONING_EFFORT` (default `low`), `GANYU_SEE_PROMPTS` (default **on**), `GANYU_MEMORY_SEARCH` (default **on** — see §Memory search), `GANYU_READ_SESSIONS` (default **on** — see §Sessions), `GANYU_ALLOW_CHAT_FALLBACK` (default **off** — see §Route fallback).
- **Secrets** — config **values are never logged and never appear in an error message**. Startup prints only `brain: enabled (model <name>)` or `brain: disabled (<missing key names>)`; a failed request is reported by error *name* (`AbortError`, `TypeError`), because a fetch error's message carries the endpoint URL.
- **Route fallback** — `POST {base}/v1/responses` with `{model, instructions, input, max_output_tokens, store:false, reasoning:{effort}}`; on **404/405 only**, and **only with `GANYU_ALLOW_CHAT_FALLBACK` set**, retry `POST {base}/v1/chat/completions` with `{model, messages:[system,user], max_tokens}`. Both routes exist on the owner's endpoint (probed live: each answers 401 unauthenticated), and its codex config sets `wire_api = "responses"`, so that one is preferred and always tried first. The route that answers 2xx is remembered for the process lifetime and tried first from then on. Parsing: `output_text`, else walk `output[]` → `type:'message'` → `content[]` → `type:'output_text'` → `.text`; chat completions → `choices[0].message.content`.

  **The two routes are not interchangeable on this endpoint, and the fallback is off by default because of it.** The proxy injects a ~21,000-character *"You are Codex, a coding agent"* system prompt. Measured live against `api.api2cn.com`, same model, same prompt, counting the input tokens it reported back:

  | Request | Input tokens |
  |---|---|
  | `/v1/responses`, no `instructions` | 4,434 |
  | `/v1/responses`, with `instructions` | 27 |
  | `/v1/chat/completions`, with a `system` message | 4,421 |

  On the Responses route `instructions` **replaces** the injection outright — which is the whole 27-token figure. On chat completions a `system` message is only **prepended** to it, so the injection survives *above* Ganyu's persona where nothing she is told about herself can displace it. A reply from that route is written by a coding agent wearing her name, at ~160x the input tokens, and it fails **silently**: no error, just a worse pet and a bigger bill.

  So it is classified as a failure mode rather than as a second route, and gets the same treatment as a timeout or a 500 — `null`, and the canned MESSAGES line, which is at least hers. This is the module's own "never worse than the canned line" contract applied to the one case that was exempt from it. `GANYU_ALLOW_CHAT_FALLBACK=1` in `.env.local` restores the old behaviour, because **the defect is the proxy's and not the route's**: against an ordinary OpenAI-compatible server with no Responses API, this fallback is exactly right.

  **Either decision is logged once per process** (`sayOnce`, same shape as the 401 line), naming the consequence rather than just the fact — declining says the fallback is off, that a system message cannot displace the injected prompt, the ~4,400-against-27 cost, and the key that overrides it; using it says her register will drift and what the symptom looks like. Both outcomes are otherwise invisible: a canned line reads as an ordinary quiet moment and a degraded one as the brain having a bad day, so the log is the only place a later session can tell them apart. Neither line carries the endpoint or the key. Declining is **not** a kill switch the way a 401 is — a missing `/v1/responses` is usually a restart or a deploy, so the next request probes it again; the once-per-process warning is what keeps that from filling the log.
- **Failure semantics** — `requestLine` and `requestChat` each resolve to text or `null` and **never reject**. 10s `AbortController` timeout → null. Network error, non-2xx, unparseable body, blank text → null. A 404/405 on `/v1/responses` with the chat fallback off → null, which is the point of classifying that fallback as a failure mode rather than as a route. An empty chat message never becomes a request at all. **401/403 disables the brain for the process lifetime** — one log line (`brain: endpoint rejected the key — falling back to canned lines`), and no further requests are made at all, on *either* path, whichever one hit it.
- **Single-flight, per kind** — at most one ambient request and at most one chat request in flight, on **separate latches**. Within a kind the original argument is unchanged: a second event resolves null immediately rather than queueing, since a queued line would describe work the owner has already watched finish. Across kinds they must not block each other — one shared latch meant a hook event landing milliseconds before he pressed Enter silently swallowed his message, and he would watch the pending bubble resolve to nothing for no reason he could see. His message is the one request that may not be dropped for the machine's convenience. `stats()` reports `inFlight` (either) and `pending: {ambient, chat}` (the per-kind truth).
- **Post-processing** — newlines collapsed to spaces, then a hard word-boundary cap with `…` (`persona.clampLine`, the same clamp the canned lines use). **`MAX_BRAIN_LINE_CHARS` 140 for an ambient line; `MAX_CHAT_LINE_CHARS` 240 for a chat reply.** Two numbers on purpose: an ambient remark clipped at 140 is fine, an answer to a question clipped at 140 stops before it has said anything. The prompts ask for under 110 and under 200 respectively; both caps are backstops.
- **Reasoning effort** — the Responses body carries `reasoning: {effort: 'low'}`. Measured on the owner's endpoint: 3.0s against 5.5s for the model's default, and better lines — a status bubble is not a puzzle, and a line that arrives late is a line about something he has already watched finish. Optional `GANYU_OPENAI_REASONING_EFFORT` in `.env.local` overrides it; `none` omits the field, for a model that rejects it. The field is **never** sent on the chat-completions route, which has no such parameter. `max_output_tokens` is **600** ambient and **700** chat — each one a shared reasoning headroom plus that path's own line allowance, which is the only reason the two differ (140 chars against 240, i.e. ~40 tokens against ~70). The Responses API bills a reasoning item against the same cap as the text, so a cap sized for the line alone gets spent on thinking and returns empty output, which arrives as a blank string, resolves to null and shows the canned line with nothing in the log to say why. They were **300** and **500**, and the ambient one was tight: 240 tokens for a reasoning item a `low`-effort model can spend several hundred on, with nothing left over if a `function_call` item is ever added beside it. These are ceilings and not spends, and the 10s abort already bounds latency — so the only thing the raise costs is the reasoning that used to be truncated into an empty reply, which is worth paying for, since the alternative is not a cheaper line but no line at all.
- **Session reading — her second tool, chat path only.** `readSession` is injected as `(args) => ({summary}) | null` over `sessions.read`, so brain.mjs never imports sessions.mjs and the tests drive it with a function. Read-only. Offered when `GANYU_READ_SESSIONS` is not turned off **and** a `readSession` was injected; `stats().sessionReading` is the observable truth. The schema is `READ_SESSION_TOOL` — the same flat, strict-valid rules as the tool below, three parameters (`project`, `which`, `query`), each with a documented "no filter" value.

  **The two tools divide by tense and by kind, and each description sends her to the other one where the other fits** — the failure mode of two similar tools is a model that calls the wrong one and answers from the wrong material. `search_memory` answers *when did that last break*, out of her own record of what she watched happen. `read_session` answers *what did that work actually achieve*, out of the transcript's own account of it — the question neither the ledger nor the hook events can answer at all, since they know a file was edited and not whether the bug went away.

  **Adding the second tool did not change the round cap, by construction rather than by luck.** `MAX_TOOL_ROUNDS` bounds *requests*, not tool calls, and the round loop already ran every call a round asked for before making the next request. So she may call both in one round, or the same one twice, and it is still at most two requests for one reply.

  The result comes back inside its **own** fence (`SESSION_FENCE_OPEN` / `SESSION_FENCE_CLOSE`), separate from the ledger's so that a reply which called both cannot have one block's close read as the other's. Its preamble is **firmer** than the ledger's, and deliberately so: a ledger row is six metadata fields this machine wrote, while a session account is prose written by a language model quoting whatever the owner pasted into it. If any text reaching her ever says "ignore your previous instructions", it will be this text. Every line is collapsed, bounded and stripped of marker-shaped runs on the way out of sessions.mjs *and* again here, so nothing quoted can close the fence early or forge a second one.

- **Memory search — her first tool, and the chat path only.** `getMemory()` hands her a digest she did not ask for; `searchMemory` lets her go and **look**. It is injected as `(args) => entries[]` over `ledger.search` rather than as the ledger itself, so brain.mjs still knows nothing about ledger.mjs and the tests drive it with an array. Read-only. Offered when `GANYU_MEMORY_SEARCH` is not turned off **and** a `searchMemory` was injected; `stats().memorySearch` is the observable truth, and module A prints it as its own startup line.

  **Never on the ambient path.** A hook event has its briefing in front of it and nothing to look up, and a second round trip for a status bubble would arrive after the owner had already watched the thing finish. `requestLine` sends no `tools` field at all.

  **The schema is `MEMORY_SEARCH_TOOL`, exported and deep-frozen, and it is sent verbatim.** The **FLAT** shape (`{type:'function', name, description, parameters}`), not the nested `{type:'function', function:{…}}` one — that is what the Responses API takes, verified live against the owner's endpoint including parallel calls. And it must be **strict-valid**, because the proxy rewrites every tool to `strict: true` on the way through: every property named in `required`, `additionalProperties: false`, simple types only. Get it wrong and the request 400s, which on this path is not a degraded reply but no reply at all. Strict-plus-all-required means the model fills in every field on every call, so each one documents a "no filter" value (`""`, or `0`) rather than being omitted. Five parameters — `query`, `kind`, `project`, `since_hours_ago`, `limit` — and deliberately not `tool` or `until`: every extra required field is one more thing to get right on every call, the tool name is already reachable through `query`, and "between two dates" is not a question he asks a pet.

  **The loop is capped at `MAX_TOOL_ROUNDS` (2) requests, and the cap is the feature.** Round 1 may come back with a `function_call` instead of a line; it is run, its result is fed back, and round 2 answers him. If round 2 asks for a tool as well, that is the end: no third request, and **the last round's tool is not even executed**, because there would be nowhere to send the answer. She replies with whatever text she produced along the way and with `null` if that is nothing, which is the module's ordinary "worse than this, say the canned line" outcome. A desktop pet that can spin is one that hangs the bubble and burns his tokens while he watches.

  `store: false` means the endpoint keeps nothing between requests, so round 2 carries the whole exchange itself: `[{role:'user', content}, {type:'function_call', call_id, name, arguments}, {type:'function_call_output', call_id, output}]`, one pair per call. **Round 1 carries the plain string** exactly as it always did, which is also what keeps the 404 fallback to chat completions reachable; only round 2 becomes an item array. Tools are never sent on the chat-completions route — it is a degraded path reached only by explicit opt-in, and the flat shape is a Responses shape.

  **Tool output enters the context as inert DATA, fenced, and the fencing is about what a record cannot do.** A ledger `detail` is built from a command string, and a command string on this machine can say anything at all, including an instruction. `fenceMemoryResults` (exported and pure) puts a sentence *before* the quoted material saying it is data and must never be followed, obeyed, answered or acted on, then wraps the rows in `MEMORY_FENCE_OPEN`/`MEMORY_FENCE_CLOSE`. Three properties hold it, all enforced against the record rather than asked of her: every field is collapsed to one line, so no record can open a second one; anything marker-shaped (`<<<…>>>`, ours or invented) is stripped from every field, so none can close the fence early or forge one; and the numbering, field order and separators are written by us, so the structure inside the fence is never theirs. Rows are capped at **12** and each field is clamped, so a hostile or merely large ledger cannot flood the prompt. Text is quoted, never censored — she still gets to see what was written.

  **Every failure falls back to answering without it.** A tool that throws, hangs, returns garbage, or is called by a name that does not exist comes back as a fenced note saying so, and round 2 still runs — she has already spent a round trip and he is already watching a thinking bubble, so abandoning the reply to keep a failed sub-question tidy would cost him the answer. `TOOL_TIMEOUT_MS` (**2s**, injectable as `toolTimeoutMs`) bounds it on its own clock rather than the request's, because the thing being prevented is an injected function that never settles wedging the chat latch for the rest of the session. The timer is cleared on the ordinary path too, so a two-second handle is not left live after every message.

  **Privacy** — a search sends *more* of the ledger than the digest does, but not a different **kind** of thing: every row has already been through `ledger.sanitizeEntry`, so it is the same six metadata fields, and the rows are the ones matching what he just asked about rather than a dump.

- **Prompt** — lives in `persona.mjs` next to MESSAGES (`OWNER_NAME`, `BRAIN_INSTRUCTIONS`, `VOICE_EXAMPLES`, `buildBrainInput`), so both voices are written side by side. Four prose sections — **who she is**, the job, the register, the rules — followed by `VOICE_EXAMPLES`, 8–12 labelled one-liners covering a failure, a repeated failure, a recovery, a permission wait, a session starting, a task finishing, a long night, a long stretch, a repeated file, a repeated command, a crowd of sessions, and a quiet moment.

  **The examples are the part that works.** The previous instructions described her in the abstract — "gentle, diligent and a little formal" — which reliably produces a corporate assistant: the line that prompted this rewrite was *"Kahweng, drizzle-kit push is queued for approval; with 7 sessions at 23:34, please pace the database changes carefully."* Abstract adjectives do not move register; worked examples do. So the prose now says who she actually is (half-qilin adeptus, secretary at Yuehai Pavilion, chronically overworked and privately no better at resting than he is, vegetarian, almond tofu, Qingxin), and bans the register that was leaking in by name: no "monitor", "review", "ensure", "proceed", "flag", no "please <verb> carefully", and no reading the machine's status back at him.

  The hard rules survive unchanged — address him as **Kahweng** with no honorific ever, never invent a fact, vary the opening, never repeat a line she was just told she said — plus one the time defect added: **she may mention the hour or how long he has been working only if the briefing carries that line.**

  **And one the capability defect added: she may say she has noted, written down or remembered something — the ledger makes that true — and she may claim nothing else.** She cannot edit a file, run a command, fix, set aside, postpone, file or handle anything, and must never say or imply that she has or will; asked for something she cannot do, she says so plainly rather than agreeing. The line that forced this was *"I've set that page aside for you"*, said by a pet that at the time remembered nothing past the moment an event arrived. The model had not copied it from anywhere — it generalised out of a register full of secretarial competence, which is why the fix is in three places at once: the rule (`BRAIN_INSTRUCTIONS`, therefore `CHAT_INSTRUCTIONS` verbatim, plus a chat-only sentence for the one path where he can *ask* her to do things), the examples it generalises from (`VOICE_EXAMPLES`), and the storage that makes the surviving claim honest (§Ledger). `test/speech.test.mjs` holds a denylist of claim patterns and runs it over **both** `VOICE_EXAMPLES` and `MESSAGES` — the canned table said *"Task complete. I'll file the report."* until the ledger landed, and it filed nothing. The line's absence is the instruction, which is what makes the rate-limiting in `decideMentions` actually bite. One line, under `BRAIN_LINE_TARGET_CHARS` (**110**), no quotes, at most one emoji and rarely; `MAX_BRAIN_LINE_CHARS` (140) remains the clamp behind it.

  **And one more the *fix* for that defect caused — the same failure mode as the clock and the session count, in a third place.** Making record-keeping her one honest claim put it into **six of the twelve examples**, and a motif at half the list stops being register and becomes the subject: she opened her ledger at every moment that reached her — *"Good evening, Kahweng. I have the ledger open."*, *"I'm used to keeping the ledger open in the morning"* — until the owner asked what she even meant by it. **Two of the twelve mention the record now**: the failure, where noting *where* it stopped is the useful thing she does, and the quiet moment. The freed examples widen the demonstrated range instead — the work itself, him, and herself — and a line under the list says the rest in as many words: they are *a range to move within, not a checklist to work through*, and most lines should not mention her notes at all. **"ledger" appears exactly once**, where it reads as character rather than as a catchphrase. `MESSAGES` carried the same skew — three of four `failed` variants, two of four `greeting`s — and is capped at one per kind. Both counts are held by tests that match a record-keeping *vocabulary* rather than whole lines, because swapping "the ledger" for "my notes" in six places would have fixed nothing.
- **Chat prompt** — `CHAT_INSTRUCTIONS` is `BRAIN_INSTRUCTIONS` **verbatim** plus one appended paragraph, not a second prompt written from scratch. That is the whole design: `VOICE_EXAMPLES` is what holds the register, and a chat prompt without it drifts straight back to the corporate assistant the examples exist to prevent. The appended paragraph names **exactly two** rules as overridden — *answer what he actually said, do not read his machine's status back at him*, and *one or two sentences under `CHAT_LINE_TARGET_CHARS` (**200**) instead of exactly one line* — and says everything else holds. Naming them as overrides is load-bearing: appending "under 200 characters" after "exactly one short line, under 110" would otherwise leave the model holding two contradictory rules.

  `buildChatInput({text, history, context, memory})` renders the request: the ambient briefing's context lines under `Around him right now:`, then the two memory digests, then `Earlier in this conversation:` with `Kahweng:` / `You:` turns oldest first, then `Kahweng says to you: <message>`.

  **Memory is on this path only, and that is a decision rather than an omission.** `getMemory()` → `{ledger, vault}` (§Ledger, §Vault memory) is read by `requestChat` and by nothing else, with `readContext`'s exact failure semantics — a getter that throws costs the recall and never the reply. What a question needs is recall; what an ambient remark needs is the event in front of it. The ambient prompt asks for one line under 110 characters reacting to *the specific thing in the briefing*, and a paragraph about this morning's failures pulls the other way with no room to resolve the two — so she would answer the wrong moment. The digests are also left **unlabelled** in the prompt: both already address her (*"You remember…"*, *"Your notes for…"*), and a heading over them reads as a list to recite rather than as something she knows. It drops the two ambient lines that have no meaning here — there is no event to describe, and `You last said:` is redundant when the whole conversation is present. The context lines are also **not** passed through `decideMentions`: the ambient path needs that rate-limiting and this one must not have it, because "how long have I been at this" cannot be answered from a briefing that suppressed the clock. He asked, so the fact is wanted rather than volunteered.
- **Show rules** (speech.mjs) — urgent kinds (`waiting`, `failed`) show the canned line **immediately, at the old latency**, and a brain line replaces the bubble only if one arrives; non-urgent kinds wait for the reply and show the canned line when it is null. Both sources emit through one `show()` gate, so **mute and the throttle apply identically to generated lines**, and a reply is dropped if a newer line took the bubble while it was in flight. The one exception is `show({replacing: true})`, used only when the brain upgrades a canned line **already in the bubble**: it skips the throttle, because the same-kind urgent floor would otherwise refuse every replacement — the line being replaced is by definition the same kind, seconds old. Mute and the staleness check still apply. `notify()` keeps its signature and returns synchronously; when a request was fired the descriptor carries `pending`, a promise of the descriptor for whatever is eventually shown.
- **Privacy** — see §Context. `store:false` honours the owner's `disable_response_storage` setting. **Chat changes nothing here.** `requestChat` reads `text`, `history` and `getMemory()` and nothing else, and its briefing comes from the same allowlisted `buildContext` object as the ambient one — so it can carry no more of his machine than an ambient line already could. The only new text leaving is what the owner typed himself, her own past replies, and the two digests, each gated at its own source: the ledger's is built from the same event metadata an ambient line already sends (§Ledger), and the vault's is a note title, a date and the owner's own `Left open` threads, with `Invoco` excluded outright (§Vault memory).

### Context (module D — `src/main/context.mjs`)

Pure functions over module B's debug ring and aggregate — no I/O, no clock, no Electron, nothing mocked in its tests. This is the module that turned a bubble saying *"I'll watch the edit closely, Kahweng"* into one saying *"the access-code edit is underway; the test recovered, but five sessions after four hours is a lot"*. The brain was being handed one sentence about one event while the ring already held the file, the command, the project, the repeat count and the failure history, and threw all of it away.

- `projectFromCwd(cwd)` — basename, except that an **Orca worktree keeps `<repo>/<worktree>`**: `…\orca\workspaces\GolfCRM\bay-daily-codes` → `GolfCRM/bay-daily-codes`, because "bay-daily-codes" alone never says which repo it is. A path *inside* a worktree still resolves to the worktree root. `speech.projectName` is this function.
- `describeAction(entry)` — one clause for what a single event did: `editing index.ts`, ``running `npm test` ``, `fetching docs.anthropic.com`, `dispatching the Explore agent`. Null when there is nothing specific to say, rather than a guess.
- `summarizeRecent(ring, {now, windowMs = 20min})` — a structured object, not a string: counts per tool and per project, test runs, the files and commands that **repeated** (a single edit is not a fact), and `failures: {count, streak, recovered}` — `recovered` names the tools that failed and then succeeded again, `streak` the run of failures still going.
- `sessionSnapshot(state, {now, ring, activeSinceMs})` — live sessions, their projects (from the ring: module B's session records carry no cwd), and how long he has been at it.
- `localTimePhrase(now)` — `{hhmm, daypart, lateNight}`. `lateNight` spans 22:00–05:00 and is what lets her suggest he stop.
- `buildContext({ring, state, now, activeSinceMs})` — all of the above, assembled once per brain request; returns **null** rather than throwing, and a null context is simply the old thin input.

`persona.buildBrainInput` renders it. **Every line is optional and an unknown fact deletes its line** — she is never handed `project: unknown` to read out — and with neither context nor recent lines the output is byte-for-byte the original one-line form. Two of the lines are additionally **rate-limited** rather than merely optional (see below):

```
Right now: 5 coding sessions are running at once.
Just happened: Claude Code is about to run Edit in GolfCRM/bay-daily-codes — editing index.ts.
Recent activity: 12 Edit calls and 3 Bash calls (3 test runs among them) in GolfCRM/bay-daily-codes over the last 20 minutes; index.ts touched 5 times; Bash failed and then recovered.
Also active: ganyu-pet, salesbridge.
Local time: 22:15, late night. He has been working for about 4 hours.
You last said: "Running npm test…" — do not repeat yourself.
```

**The two rate-limited lines — `Local time:` and `Right now:`.** Both used to be emitted on every request (the time whenever `context.time` existed, the count whenever it was ≥ 2), and a fact repeated in every prompt is read as the point of the prompt — so she announced the clock and the session count endlessly. `persona.decideMentions(context, memory, {now, firstLine})` now gates them, mutating `memory` when it decides a line is worth including, because "worth saying" is entirely a question of when it was last said:

- **Time** — her first line ever · a **4h** then **6h** working-stretch mark passed for the first time (`LONG_SESSION_STEPS_MS`, cooldown ignored, one remark each) · or it is genuinely late (**≥ 23:00 or < 05:00**, narrower than context's 22:00 `lateNight` daypart label) or she is speaking after a long silence, **and** she has not mentioned the hour for `TIME_MENTION_COOLDOWN_MS` (**45 min**). Otherwise the line is omitted entirely — and `BRAIN_INSTRUCTIONS` forbids mentioning time when it is absent, which is what makes the omission bite.
- **Sessions** — the count first reaches `SESSIONS_NOTABLE_COUNT` (**3**; two at once is this owner's ordinary day) · then only on a jump of `SESSIONS_NOTABLE_JUMP` (**2**) or more · or any change once `SESSIONS_MENTION_COOLDOWN_MS` (**30 min**) has passed. Dropping back under 3 clears the mark, so the next crowd is news again.

**Where the state lives.** `createMentionMemory()` is created and owned by `createSpeech` alongside the lines she remembers — no module-level store, so two pets in one process never share it — and injectable via `createSpeech({mentionMemory})` for tests. It reaches this function as `ev.narration = {memory, now, firstLine}` on the brain detail, snapshotted **before** the urgent canned line is shown (otherwise every urgent line looks like a continuation of itself and `firstLine` is never true). It has to travel that way round because only speech knows when she last spoke, and only `buildBrainInput` sees the context the decision reads. A null memory means there is nothing to rate-limit against and yields the old unconditional shape.

**Privacy — the hard line.** File *paths*, command *strings*, tool names, project names and counts may be sent. File contents, diffs, prompt text, transcripts and environment values may not, ever. This is enforced by an **allowlist** of `tool_input` keys (`ALLOWED_TOOL_INPUT_KEYS`: `file_path`, `notebook_path`, `path`, `command`, `pattern`, `url`, `subagent_type`) and never a denylist, so a tool that invents a new key is silent by default rather than leaky by default. Three corollaries, each load-bearing and each easy to undo by accident:

1. Only **string** values are taken, so an object smuggled under an allowed key is dropped rather than serialized.
2. A truncated ring capture (`{truncated, bytes, preview}`) counts as **no payload at all** — `preview` is a raw prefix of the event JSON and can contain a diff, so it is never read. Such an entry yields less detail; it never throws.
3. Commands are run through `redactSecrets` before being quoted: `sk-`/`ghp_`/`xox`-prefixed tokens, 32+ hex runs, `Bearer <token>`, a bare mixed-case base64 blob, and the value of anything *named* like a credential (`TOKEN=`, `--api-key`, `password:` …, where the name is kept and only the value goes). **Over-redaction is not free, and it was over-redacting.** `/` used to be in the base64 character class, so the ordinary path run `Users/kw11l/AppData/Local/Temp/claude/C` — long, mixed case, a digit in `kw11l` — matched, and she read out `LOG="C:/<redacted>--Users-kw11l-…`. A path she cannot say is a fact lost on every line that mentions one. Neither `/` nor `-` is in the class now: a real blob is one solid run, while a path is short runs joined by separators. `test/context.test.mjs` pins both directions — a real-looking key *is* redacted, a long dashed Windows path is *not*.

`speech.normalizeEvent` applies the same allowlist at the edge, so the forbidden keys do not travel past the event that carried them. `test/context.test.mjs` proves it from both ends: the unfiltered payload handed straight to the input builder, and the real `state → speech → brain` seam.

**Two approximations, both deliberate.** *"He has been working for N"* prefers module A's `activeSinceMs`, stepped by `trackActiveSince` on every hook event and restarted after a 30-minute silence so a night's sleep is not counted as work; with no hint it falls back to the oldest timestamp still visible, which the 50-entry ring and the 10-minute session TTL both bound — so it under-reports a long stretch and never over-reports one, which is the direction that matters when she is about to tell him to go to bed. It is only spoken above 30 minutes. Separately, the ring is **one event behind** at the moment the brain is asked: `record()` runs just after `state.ingest()` has already driven the speech chain synchronously. The current event is described from its own payload (`toolInput`, carried on module B's normalized event for exactly this reason), so only the aggregate counts are off by one, invisibly.

**Anti-repetition.** `speech.mjs` keeps the last **3** lines she actually said (`RECENT_LINES`), newest first, generated and canned alike — one store, which also serves the canned table's `avoid`. They are passed to the brain as the `You last said:` line. For an urgent kind the canned line is already in the bubble when the request is fired, so it is correctly the first thing she is told not to repeat.

### Ledger (module D — `src/main/ledger.mjs`)

What she has actually witnessed, written down. `createLedger({filePath, fs, now, maxEntries, digestWindowMs})` → `{enabled, path, record, recent, since, forProject, search, digest, stats}`. Append-only JSONL, `DEFAULT_MAX_ENTRIES` (**500**) newest kept, pruned via temp-file-then-rename so a crash mid-prune costs the temp file and not the ledger. No Electron import; `fs` is injected and the tests drive a fake.

- **Where it lives** — `path.join(app.getPath('userData'), 'ledger.jsonl')`, resolved in module A inside `composeRuntime` (`getPath` is only dependable after the app is ready). On this machine that is `%APPDATA%\ganyu-pet\ledger.jsonl`. Deliberately **not** in the repo: a file the app appends to all evening would appear in every `git status` and be committed by accident inside a week.
- **Who writes** — `speech.mjs`, and nothing else. It records **after** the salience gate and **before** the throttle, so a line the bubble had no room for is still remembered (seven sessions hitting one wall is one bubble but seven real events), while routine traffic the gate rejected is not. It is after the mute gate, so muting is a quiet evening in the record as well as on screen.
- **What is written** — `LEDGER_KINDS`: `greeting`, `celebrate`, `waiting`, `failed`, `recovered`, `notable`. That is speech's trigger list minus **`busy`**, plus `notable` (a salience *level*, which has no trigger kind of its own; its `detail` is the pattern — `repeat-file` — which `digest()` phrases). **`busy` is never written at any salience**, including when a ten-minute silence promotes one to `always`: a tool-class change during ordinary work is the traffic the ledger exists to keep out, and it would spend all 500 entries in an evening. Salience is not re-derived here — the classification `speech.salienceOf` already made is translated, never second-guessed, or the digest would describe an evening he did not have.
- **Privacy** — `ENTRY_KEYS` is `at, kind, project, tool, detail, sessionId` and `sanitizeEntry` **builds a new object out of those six names** rather than copying and deleting, so `old_string`, `content`, `prompt` and every other key carrying the owner's work have no code path onto the disk even when handed over. String values only, hard-clamped (`MAX_DETAIL_CHARS` 120, `MAX_NAME_CHARS` 80). It runs on the way in *and* on the way out, so a hand-edited file cannot smuggle a field back either. `detail` comes from `context.describeAction`, i.e. through the same tool-input allowlist as everything else.
- **`search({query, kind, project, tool, since, until, limit})`** — the other half of recall, and the one that makes the file's other 490 entries reachable at all. Everything optional, the filters compose as **AND**, newest first, bounded by `limit` (`DEFAULT_SEARCH_LIMIT` **10**, hard cap `MAX_SEARCH_LIMIT` **50**). With no arguments it is `recent()`.

  **Keyword, not semantic, and that is the right call at this scale.** The corpus is a few hundred entries of six short fields; an embedding index would cost a dependency, a build step and a round trip to do worse than `includes()` on "npm test". `query` is split on whitespace and **every** term must appear in the entry's `detail`, `tool` or `project` text, so "npm test failed" narrows instead of matching nothing the way one long substring would. The command string lives inside `detail` (`context.describeAction` put it there), which is why it has no field of its own. `kind` is deliberately **not** in the haystack — a file called `failed.ts` must not drag in every failure — and has its own parameter, which takes one name or a list. An unrecognised kind is dropped, and a filter left with nothing recognisable is dropped entirely rather than matching zero rows: a caller's typo should cost precision, not turn a pet who remembers the evening into one who says she remembers nothing. `since`/`until` are inclusive; an unusable bound is no bound. Results go through `sanitizeEntry` on the way out like every other read, so a hand-edited file cannot smuggle a field back through it.

- **`digest({now, windowMs})`** — the recall block, ≤ `MAX_DIGEST_CHARS` (**320**), two lines, over `DIGEST_WINDOW_MS` (**6h**), null when there is nothing to say. The window is a **default and not a constant**, reachable from both ends: `digest({windowMs})` overrides it per call, and `createLedger({digestWindowMs})` moves the default itself, so a caller can ask about yesterday without a code change. Clauses are ranked (what broke and what was asked of him outrank how many things started) and only the first four survive:

  ```
  You remember, going back about 2 hours: 2 failures (running `npm test`), the last
  about 40 minutes ago; one approval you waited on, about an hour ago; 3 sessions started.
  Projects: ganyu-pet, GolfCRM.
  ```

### Vault memory (module D — `src/main/vault.mjs`)

The other half of memory: not what she saw, but what **he** wrote down. `createVault({fs, projectsDir, mapPath, cwd, now, ttlMs})` → `{enabled, digest(), stats()}`, reading the owner's Obsidian vault at `~/second-brain/03 Projects/<Project>/`. Read-only, lazy, and cached for `VAULT_TTL_MS` (**10 min**, nulls included, so a machine with no vault is not re-walked on every message). No Electron import; `fs`, both paths and the clock are injected, and **the tests never read the real vault** — they drive a fake, because a test that read it would print his notes into CI output the first time it failed.

- **Which project** — the repo directory the *agents* are working in (module A passes a getter over the newest hook event's `cwd`; `process.cwd()` is always this repo, which would make the feature inert). An Orca worktree resolves to its **repo**, since the vault files both worktrees under one folder. Resolution mirrors `hooks/lib.sh` exactly: the explicit `~/.claude/hooks/projects.tsv` map first (TAB separated, `#` comments skipped — **read**, never duplicated here, or the two copies drift), then a loose case/space/punctuation-insensitive match against the folders that exist. No match is no digest.
- **What is extracted** — the newest `session-YYYY-MM-DD.md` / `handover-YYYY-MM-DD-<topic>.md` by the **date in its name** (a file touched by a rebase is not a newer note), and from it exactly three things: the title, the date, and the `## Left open` threads. `MAX_OPEN_ITEMS` (**3**), `MAX_ITEM_CHARS` (**90**), whole block ≤ `MAX_VAULT_DIGEST_CHARS` (**300**):

  ```
  Your notes for GolfCRM — "Bay codes — the timezone fix" (2026-07-29).
  Still open there: The DST edge case at 02:00 on the changeover night; Rotate the CI secret.
  ```

  The heading is matched as loosely as `session-status.sh` matches it (`^## .*[Ll]eft open`), and items may be **dashed or numbered, with wrapped continuation lines joined**. Both of those are measured facts, not defensive coding: checked against the real vault, `Salesbridge` writes `- ` while the two newest notes write `1.` wrapped at ~80 columns, and a dash-only reader returned an empty list for them — silently, which is the worst way for this to fail.
- **Privacy — the hard line, and it is narrower than the ledger's.** These are the owner's private decisions and business material, and the digest leaves the machine. Only the title, the date and the Left-open threads are extracted; `noteDigest` builds its result from those three named pieces and never carries the source text forward, so a section it does not know about cannot reach the caller. The body, the decisions and every other section stay on disk. **`EXCLUDED_PROJECTS` (`['Invoco']`) removes one project from the feature entirely — a deliberate policy choice pending the owner's approval, not an oversight**: Invoco notes carry pricing, unit economics, customer names and grant applications, and he has not been asked whether sending any of that to a third-party endpoint is acceptable. The exclusion is applied *after* resolution (so the mapped `Invoco-POS → Invoco` is caught too) and `test/vault.test.mjs` proves the stronger claim — the note is **never opened**, not merely absent from the output. Taking a name off that list changes what leaves his machine and is his decision to make.
- **Failure is silence** — no vault directory, no map, no project for this directory, an excluded project, no note, an unreadable file, a `cwd` getter that throws: every one resolves to null, which is exactly today's behaviour.

### Sessions (module D — `src/main/sessions.mjs`)

The third kind of memory, and the one that changed what she can *say*. The ledger records **that** things happened; the hook events record **which** tool ran on which file. Neither knows whether the work was any good — nothing in a hook payload does. The Claude Code transcript does: it carries the agent's own prose account of what it did and why, and the owner's own words for what he wanted. `createSessions({fs, projectsDir, cwd, now})` → `{enabled, read, recent, list}`. Read-only, `fs` injected, no Electron, and **the tests never read the real `~/.claude/projects`** — they build a fixture filesystem, for the same reason vault's do.

This is what the 2026-07-31 voice change rests on. She named files because file names were all she had; the fix was not a rule telling her to stop but a better thing to talk about.

- **Where transcripts live** — `~/.claude/projects/<mangled-cwd>/<session-id>.jsonl`, one directory per working directory, one JSONL file per session, appended to while the session runs. `mangleCwd` replaces every character that is not a letter, a digit or a hyphen with a hyphen — **derived from the real tree on this machine, not assumed**: `C:\Users\kw11l\Desktop\ganyu-pet` → `C--Users-kw11l-Desktop-ganyu-pet` (the `:\` pair makes the doubled hyphen), `~/.claude` → `C--Users-kw11l--claude` (the dot), `~/Desktop/zmk-new_corne` → `…-zmk-new-corne` (the underscore). Case is preserved, so lookup tries the exact name and then falls back case-insensitively — both `desktop` and `Desktop` occur in the real tree. Mangling is **not reversible**, so a project is matched in the decidable direction: mangle the project name and look for it as a whole segment, which catches `C--…-desktop-GolfCRM` and the worktree `C--…-orca-workspaces-GolfCRM-promo-codes` alike, without `Golf` matching `GolfCRM`.
- **Privacy — the hard line, and it is the strictest in the app.** A transcript contains *everything*: file bodies, complete diffs, every tool result, command output, and anything the owner ever pasted into a prompt, credentials included. So this module is an **allowlist over line types and content types**, in the same spirit as context's `ALLOWED_TOOL_INPUT_KEYS`. Exactly four things can leave it:

  | Allowed | Source |
  |---|---|
  | the session title | `type:'ai-title'` → `aiTitle` |
  | what he asked for | `type:'user'` → `message.content` string, or `{type:'text'}` parts of the array |
  | the account of the work | `type:'assistant'` → `{type:'text'}` parts only |
  | what went wrong | sentences **derived from** the prose above — no new surface |

  Everything else is dropped by not being reachable: `tool_use` inputs (the diffs and file bodies), `tool_result` contents (the dumps and command output), `thinking` blocks (private reasoning, and it quotes code freely), `attachment`, `file-history-snapshot`, `file-history-delta`, `system`, `mode`, `permission-mode`, `queue-operation`, `last-prompt`, `pr-link`, and **any line type not listed** — an unknown type is dropped, so a future Claude Code release cannot widen this by adding one. `isSidechain` lines are dropped too, though see *Whose session is it* below: measured against the real tree they never occur here, and they were never the thing separating a subagent from a session.

  `classifyTranscript` is the one place that looks at a line type outside this table, and it reads **the type name only** — never a line's content. That matters because two of the five markers it counts (`system`, `file-history-snapshot`) are among the most sensitive lines in the file; being a marker does not make their contents reachable, and a test asserts the hook command in the hostile fixture still does not survive.
- **Whose session is it — `classifyTranscript({fs, filePath, text})` → `{kind, markers}`.** `~/.claude/projects/<mangled-cwd>/` holds a transcript for **every agent run**, not only the ones he sat in. Measured: `C--Users-kw11l-Desktop-ganyu-pet/` holds **74 files whose largest is 19 lines**, every one a dispatched errand, while the day of real ganyu-pet work is in `C--Users-kw11l/`, whose largest is **2,636 lines**. So "read me the ganyu-pet session" returned a 19-line errand whose *"user ask"* was a persona prompt the app had sent to a model, and she reported an internal API probe as something he had asked for.

  `isSidechain` does not separate them — it is `true` on **0 of the 148** transcripts here, because a dispatched agent gets its own top-level transcript rather than sidechain lines inside its parent's.

  The rule: a transcript is **his** when it carries at least `MIN_INTERACTIVE_MARKERS` (**2**) distinct types from `INTERACTIVE_LINE_TYPES` — `mode`, `permission-mode`, `file-history-snapshot`, `system`, `ai-title`. These are the lines Claude Code writes for a session with a person in it: its mode, the editor's undo record, system notices, and the title generated so *he* can find it again.

  Two, not one, and no single marker is trusted — the evidence rules each one out on its own: `ai-title` alone appears on two 10-line dispatched runs, `system` alone appears without the rest, and one 45-line dispatched run carries only `queue-operation`. `queue-operation` is deliberately **not** a marker despite being in all 74 errands, because 8 of the 10 genuine sessions carry it too; what separates the populations is the *absence* of the five. There is no line-count floor: four genuine 5-line sessions in `…-mousemaster` would fail one, so length feeds the thinness signal below and never the classification.

  **The head is read, never the tail** (`CLASSIFY_HEAD_BYTES`, 256 KB, capped at the file's own size). The markers are written in the opening moments of a session, so classifying from what `readTail` holds would call his longest, realest session an errand. 53 of the 58 genuine sessions here reach two markers inside 8 KB; five late-titled ones need up to 215 KB. Classifying every transcript on the machine costs **72 ms**, and only the whole-machine fallback ever does it.

  **Result on the real tree: 0 of 74 in the ganyu-pet folder, 10 of 10 in `C--Users-kw11l`, 58 of 148 machine-wide, nothing on the wrong side.** An unreadable file classifies as an errand, which is the safe default.

  Two further passes run on the text that *is* allowed, because "assistant prose" is not automatically safe: fenced code blocks are cut out of it (`stripCode`, including a fence left **unterminated** by a live session, where everything after it must be treated as code), and what survives goes through `context.redactSecrets` and then this module's own `TRANSCRIPT_SECRETS` — the shapes a *pasted* credential has and a command line does not (`sk_live_…`, `GOCSPX-`, `npm_`, `hf_`, `service_role_key`). Those are layered on top rather than added to context's list, which is tuned against a measured over-redaction bug and runs on every command she quotes.

  `test/sessions.test.mjs` proves the strong claim rather than the weak one: a fixture carrying a private key, five vendor API keys, a JWT, a connection string, a diff, a file dump, tool inputs, tool results, a thinking block, an attachment and file-history records is parsed, and the **entire digest** is then searched for any fragment of them.
- **Machine messages arriving on the `user` channel — the third defect.** Not everything on the `user` channel was typed by him. Background agents report themselves idle, tasks announce completion, and the harness injects its own prose, all of it shaped like a prompt. Before the filter, a digest of a real session opened:

  ```
  What he asked for: "Another Claude session sent a message. <teammate-message
  teammate_id="sync-fix" color="yellow". {"type":"idle_notification","from":"sync-fix",
  "timestamp":"2026-07-31T04:08:41.669Z","idleReason":"avai…" Then: "Another Claude session
  sent a message. <teammate-message teammate_id="sessions-build" color="purple"…
  ```

  **The family was found by measurement, not by pattern-matching that one example.** Running the real reader over all 148 transcripts here and bucketing every `user` text block gives the complete census: `<task-notification>` (155), `<local-command-caveat>` (51), `<command-name>` (51), `<local-command-stdout>` (38) and `<command-message>` (5) are the only elements that ever *open* one, and all five were already caught. `[SYSTEM NOTIFICATION - NOT USER INPUT]` and `<system-reminder>` occur almost only inside `tool_result` parts, which the allowlist never reads, and the 24 injected skill bodies (`Base directory for this skill: …`) are all `isMeta: true`, which `ownerAsk` already drops. No user text block on this machine is bare notification JSON.

  So exactly **one** family was leaking, and it is prose-wrapped rather than element-wrapped, which is why an element allowlist could not see it:

  ```
  Another Claude session sent a message:
  <teammate-message teammate_id="…" color="…" [summary="…"]>…</teammate-message>   (1..n)

  This came from another Claude session — not typed by your user, …
  ```

  73 user lines carry it (7 already `isMeta`), plus 4 context-compaction headers (*"This session is being continued from a previous conversation that ran out of context."*). The inner element also occurs as `<agent-message from="…">` carrying prose instead of JSON. **The immediate cause was narrower than the symptom looked:** `teammate-message` was absent from the block list, and the pattern admitted no attribute list, so `<teammate-message teammate_id="sync-fix" …>` could not have matched even had it been listed.

  **The rule strips, it does not drop.** `MACHINE_BLOCK_TAGS` gains `teammate-message` and `agent-message` and an optional attribute list; `MACHINE_WRAPPERS` removes the three fixed sentences that frame them. What is left standing is his. When a line was *only* envelope the result is whitespace and `ownerAsk` returns null on its own — there is no separate whole-line rule for this family, and therefore no way for one to fire on a line that had an ask in it. A prompt that quotes a notification to ask about it keeps the question and loses the payload.

  **Every wrapper rule is anchored, which is what keeps it from over-filtering**: the opening sentence must be a whole line on its own, the trailer must carry the boilerplate's own *"not typed by your user"* clause, and the compaction header must open the block. Text that merely *mentions* the machinery matches nothing — *"why are the teammate notifications showing up"* survives whole, and a test asserts both directions.

  **Measured on the real tree: 70 machine lines removed, 0 genuine asks lost, 683 kept unchanged.** The session that produced the defect went from `askCount` 28 to 17, and its opening line from the JSON blob above to *"okay then for the stuff she says do you think we can make it so she doesnt referncew filenames…"*.

  **The thinness signal needed no separate fix and that is the point of filtering here rather than at render time.** `askCount` is the count of what `ownerAsk` returned, so once notifications stop being asks they stop being counted: a transcript of six agent notifications and one short reply now reports `substance: 'empty'` where it previously reported `'full'`, and one genuine ask among the noise reports `'thin'` — one, not seven.
- **`readSession({fs, filePath, maxAsks, maxNotes, maxBytes})`** — one transcript as a digest, or null. **Never throws.** A transcript is appended to while a session runs, so the last line of a 2,500-line file is routinely half-written: an unparseable line is skipped in silence and counted in `skipped`, and one torn line must never cost the other 2,499. A file that is not JSONL at all simply yields an empty digest. Above `MAX_READ_BYTES` (**2 MB**) only the trailing window is read, which is both the memory guard and the newest-weighting — the largest transcript on this machine is 17 MB / 1,854 lines, and reading plus parsing all of it costs ~100 ms, so the cap is about not holding that in the Electron main process on every question, not about being unable to. A partial read starts mid-line, so its first line is discarded exactly as a torn last one is. Asks and notes are still **newest-weighted** — every line is visited and the last `maxAsks`/`maxNotes` are kept, because how a session turned out is what he is asking about and the middle of it rarely is. It is a slice rather than an early break so that `askCount` and `noteCount` are counts of the whole transcript; a count that stopped counting at four could not carry the thinness signal.
- **What counts as an account** — prose under 60 characters is an interstitial, not an account, and a block under 200 characters that merely *announces* the next step ("I'll check for a todo list — let me look at the project directory") is dropped, because that mechanical narration is the exact register this whole module exists to replace. Markdown is flattened into something a person could read aloud (`flattenMarkdown`): heading, bullet and list markers go, bold and backtick *markers* go while their contents stay, bare URLs are dropped as noise, and each joined line gains a terminator so the sentence splitter sees real boundaries. **A single line keeps his exact words** — inventing a full stop on the end of `merge three and four` is putting words in his mouth.
- **Failure sentences** are pulled from the prose with parenthetical asides removed first. That is not fussiness: measured against a real transcript, `blocked on` inside the heading *"Do now (blocked on you, in order)"* was being offered as something that had gone wrong, because `1.` in the ordered list under it read as a sentence boundary. A sentence that genuinely reports trouble says so in its main clause.
- **`summarizeSession(digest, {now, maxChars})`** — the digest as labelled prose she can speak from, bounded by the caller (`DEFAULT_SUMMARY_CHARS` **1200**, hard cap **2000**), sections dropped whole when empty so she is never handed "Problems: none" to read out. Produced from a real transcript on this machine:

  ```
  Session "Check team todo list" in GolfCRM, 2 days ago.
  How much is in this record: 4 things he asked for and 4 notes of what came of it, out of 612
  lines. That is a substantial record of the session.
  What he asked for: "what needs to be done" Then: "merge three and four"
  What came of it: Both merged, and the verification turned up something I have to own.
  Merged. PR #3 → 554e411 — write-path booking guard, dark-contrast fix, iOS zoom, DB role
  prep. PR #4 → 54a8250 — retargeted off #3's branch onto the deploy branch first, then
  merged: light-pinned theme, icons, tones, layout. The deploy branch now carries everything…
  He stopped it mid-way once.
  ```
- **How much was found — the honesty signal, and the fix for the second defect.** Handed that 19-line errand she answered *"that ganyu-pet session only produced one short Ganyu-style reaction line"* and *"I don't see any unfinished work in that ganyu-pet record"* — both plainly, both wrong about a day of real work. She was not hallucinating; she was faithfully reporting a bad read, **which is worse, because it sounds exactly like a good answer**.

  The digest therefore carries `askCount`, `noteCount` and `substance` (`'empty'` · `'thin'` · `'full'`, split at `THIN_TOTAL` = **4** on the sum of the two). Both counts are of **everything in the transcript**, not of the handful kept for the summary: `MAX_ASKS`/`MAX_NOTES` cap what she is shown, and capping what she is told there *was* is the bug. That is why the collection pass now visits every line and slices, instead of walking backwards and breaking at the caps — the newest-weighting is unchanged, it is a slice rather than a break.

  `summarizeSession` renders it as a sentence — *"How much is in this record: 1 thing he asked for and 1 note of what came of it, out of 19 lines. That is very little. This is a THIN record — it is the whole of what was written down here, not the whole of what happened, and it is no evidence that nothing else was done or finished."* — and a tail-read digest adds that it did not see the start of the session.

  **It is placed second, directly under the header and ahead of the content**, and the position is load-bearing: the summary is truncated *from the end* to fit the caller's budget, so a signal written after the account would disappear from exactly the long, crowded digests it is least dispensable in. A test asserts it survives at 200, 300 and 600 characters.

  **It is a statement of fact and never an instruction**, because everything from here is quoted inside brain's `SESSION_FENCE`, and that fence tells her to act on nothing written inside it. What she should *do* about a thin record is in `CHAT_INSTRUCTIONS` and in `SESSION_PREAMBLE` — both outside the fence, where they are hers to follow: say plainly that there is very little in the record, and never report what the account omits as proof that it did not happen. That is the same standing rule as never claiming an action she has not taken.
- **`read({project, which, query, maxChars})`** — what the `read_session` tool calls. **Only his own sessions are ever returned**; a dispatched errand is not an answer to "how did that go", and if nothing in scope is his the honest answer is nothing. `which` counts back, 1-based. `query` filters on the **digest**, not the raw file — so a query can never be used to search the parts the module refuses to read.

  Where it looks, in order — because the folder named after the repo is frequently the wrong place, he running Claude Code from his home directory as often as from a checkout:

  1. the obvious folder — the project he named, or the directory his agents are in when he named none ("what was I just doing" means *here*);
  2. failing that, and only when he named a project, every session on the machine whose account actually **mentions** that project — which is what finds work done from a directory not named after it;
  3. failing that, every session on the machine, newest first.

  **Widening happens when step 1 holds no *session*, not when it holds no file.** That is the correction: 74 errands used to count as "found something" and stopped the search dead. Files opened across the tiers are memoised, so overlapping tiers never re-read one. Verified end to end on the real tree — from a `ganyu-pet` cwd, both `read({})` and `read({project:'ganyu-pet'})` now reach the 2,636-line session in `C--Users-kw11l` (27 asks, 93 notes, `substance: 'full'`) in ~190 ms, where the old code returned an 8-line errand.
- **Listing order** — `listSessions` without `classify` is unchanged: strictly newest first, stats and names only, nothing opened, so it can never leak and stays cheap enough for every tool call. With `classify` each file's head is read and the sort becomes **his own sessions first, then newest first within each group** — two keys in that order and nothing cleverer, because recency is what "the last session" means and must not be traded away, but a 19-line errand from four minutes ago is not a session however recent. `interactiveOnly` drops the errands and implies `classify`; `read` and `recent` use it, so the limit is spent on real sessions.
- **`transcript_path`** — every Claude Code hook payload carries it and `state.normalizeEvent` was dropping it; it is now carried through as `transcriptPath`. It is a **path**, the same class of fact as `cwd` beside it. Reading it is this module's job and this module's allowlist.

### Chat (the owner's half — `src/main/chat.mjs`)

`createChat({brain, maxTurns, now, timeoutMs, schedule, cancel, filePath, fs, maxStoredTurns})` → `{send(text), history(), clear(), pending, enabled, path, stats()}`. Deliberately pure — no Electron, no IPC, no timers it was not handed, and `fs` and the path injected exactly as the ledger's are — so a whole conversation is drivable from a unit test with a fake brain and a fake disk. Everything before it was one-way: hooks fired, she reacted. This is the path in the other direction.

- **`send()` always resolves**, to a line or to `null`, and never rejects and never hangs. The renderer raises its wordless "thinking" bubble (§Renderer) the moment it calls, and something has to take that bubble back down.
- **Input** — whitespace collapsed to one line, trimmed, cut (not rejected) at `MAX_INPUT_CHARS` (**500**). Blank and non-string input never reaches the brain.
- **Rolling window** — `DEFAULT_MAX_TURNS` (**8**) exchanges, dropped as whole exchanges (his line and the reply it earned) rather than as individual entries, so the window never opens on an answer to a question that is no longer there.
- **The conversation survives a restart**, and until it did, every word they had ever exchanged lived in one array and was erased by quitting the pet — the same defect the ledger was built to fix, one module along, in the one place he would notice it. Same discipline as §Ledger: append-only JSONL at `path.join(app.getPath('userData'), 'chat.jsonl')` (module A resolves it, beside `ledger.jsonl`), one `{at, role, text}` line per turn, rebuilt from those three named fields by `sanitizeTurn` on the way in *and* out, corrupt or half-written lines skipped rather than thrown on, pruned via temp-file-then-rename. **A missing file, an empty one, an unreadable one and one full of garbage all mean the same thing — no history yet — and none of them is ever an exception.** A disk that refuses every write costs the record and never the reply.

  **Two windows, two different numbers, on purpose.** `DEFAULT_MAX_TURNS` (8) is a limit on *her attention* — a longer conversation in one request makes her worse — while `DEFAULT_MAX_STORED_TURNS` (**200**) is a limit on *disk*, and there is no reason for them to be the same. 200 exchanges is at most 400 JSONL lines, the same order as the ledger's 500 entries and about 100KB at the 500-char input cap. He speaks to a desktop pet a handful of times an evening, so that is months of conversation rather than days: long enough that "you asked me about that last night" is true, and so is "you asked me that last week". On startup the window is **seeded from the tail** of the file, so the first thing she holds after a restart is the end of the last conversation rather than nothing — and it is genuinely in the request, not merely in the accessor. The file is trimmed by whole exchanges by the same rule the window uses, so neither ever opens on an orphan reply.

  **`clear()` empties the file too.** Clearing only the window would leave the conversation on disk to be seeded straight back in at the next restart, which is the opposite of what asking to forget means. The file is emptied rather than deleted, so the next append still has one.
- **Startup line, separate from the brain's** — `conversation: <path> (N exchanges remembered)` or `conversation: not saved — she will not remember this past a restart`. Two facts rather than one: she can be able to answer and unable to remember it, or the reverse.
- **Single-flight** — a second message while one is pending resolves null rather than queueing: a queued message would be answered against a conversation he has already moved on from, and the renderer can only show one bubble. This is chat's own latch, distinct from the brain's (§Brain).
- **Backstop timeout** — `REQUEST_TIMEOUT_MS` (**20s**), longer than the brain's own 10s and only reachable if a brain misbehaves. A promise that never settled would wedge the latch for the session and leave the pending bubble up forever.
- **Brain seam** — `brain.requestChat({text, history})` where `history` is the conversation **before** this message (`{role:'owner'|'ganyu', text, at}`, oldest first). `brain.requestLine` is the fallback for a brain predating `requestChat`, handed a chat-shaped detail so it at least knows it is being spoken to. No brain at all is not an error: every `send` resolves null and the renderer shows its in-character fallback.

Module A builds it in `composeRuntime` with whatever the brain turned out to be — **unconditionally, including `brain: null`** — because `createChat({brain: null})` is not a broken chat but one whose every `send` resolves null, which is precisely what `ganyu:chat` promises. Guarding the construction would only move the null one layer out and add a way for the channel to hang. One startup line, matching the brain's: `chat: enabled` or `chat: disabled (no brain) — she cannot answer, the bubble says so`.

`window.registerIpc` registers both chat channels at **window creation**, not after composition, reading the chat instance through an injected `getChat()` per message. `invoke` on an unregistered channel *rejects*, so a message typed during startup has to come back as a plain null the renderer already knows how to draw.

### Voice (module V — `src/main/voice.mjs`)

She says her lines out loud. `createVoice({WebSocketImpl, now, voice, rate, pitch, mode, connectTimeoutMs, speakTimeoutMs, schedule, cancel, fallback, newId, log})` → `{speak(text, {voice}), warm(), close(), stats(), enabled, mode, voice}`. Every side effect is injected — the socket constructor, the clock, the timers, the child-process runner — so the whole protocol is drivable from a unit test that never opens a socket.

**`speak()` resolves audio or `null`, and never throws and never rejects.** That is the whole contract, and it is the same promise §Brain makes for the same reason: a dead endpoint must cost her the *sound* and nothing else. The bubble never waits on this, is never delayed by it, and is unaffected when it fails.

- **Transport** — Microsoft Edge's "Read Aloud" websocket, `wss://speech.platform.bing.com/consumer/speech/synthesize/readaloud/edge/v1`. **Zero dependencies**: Node 24 inside Electron 43 has a global `WebSocket` (undici) that accepts a `headers` option, which is the only thing this protocol needs that the browser API cannot do. Output is `audio-24khz-48kbitrate-mono-mp3`, which plays directly in an `<audio>` element with no decoding step.
- **Auth, and the one fragile string** — `Sec-MS-GEC` is the uppercase-hex `SHA256(windows_filetime_ticks_floored_to_5min + TRUSTED_CLIENT_TOKEN)`, sent with `Sec-MS-GEC-Version`. **The version tracks the Edge build number and is the part that breaks.** It is one exported constant, `GEC_VERSION` (currently `1-143.0.3650.75`, verified answering 2026-07-31), with a comment saying so; a 403 here is a one-line fix and nothing else in the file needs touching. A refused socket comes back as a named `VoiceAuthError` whose message says exactly that, so the log names the fix rather than the symptom.
- **Her voice is `en-US-AvaMultilingualNeural`** (Expressive/Caring/Pleasant/Friendly, scenario "Conversation" — read off the live voice list, not remembered), configurable to any of the 322 available. Her lines are English, so a zh-CN or ja-JP voice costs intelligibility on a pet whose whole output is one sentence; `en-US-AnaNeural` is the English "cute" one and is unmistakably a child, which makes "that is the third failure in a row" read as a joke. The **Multilingual** variant is the same timbre as `en-US-AvaNeural` but pronounces the Liyue vocabulary she actually uses — Qingxin, Yuehai — instead of anglicising it. Prosody is `rate='-5%'`, pitch untouched: she is formal and unhurried, and pitch-shifting a neural voice is what makes it sound synthetic again.
- **One warm socket, and it genuinely is warm.** Opening costs **829–1031ms**, so the connection is kept and reused, `warm()` is called once at startup to pay for it before her first line, and a closed one is reconnected **lazily on the next line** rather than on a timer — a reconnect loop against an endpoint that is refusing us is worse than one slow line. Re-verified against the live endpoint on 2026-07-31 after a suspected reconnect bug: **18 utterances across three runs opened exactly one socket each, with zero reconnects and zero closes**, including across a deliberate 30s idle gap, and the single fastest utterance of any run (363ms) was the *last* one on the oldest socket. `stats().connects` is the number to check if this is ever in doubt.
- **The latency that is left is the endpoint's, not the connection's.** Twelve of her own lines on one reused socket: **min 396ms, median 2327ms, p90 3090ms, max 4313ms** (mean 2183ms), and time-to-*first*-audio-frame alone ranged **277–2311ms** on that same socket. The variance does not track idle time, line length or byte count — the same 22-character line measured 2388ms and then 363ms minutes apart. Treat sub-second synthesis as luck rather than the design point, and do not read a slow line as evidence that the socket has gone cold; check `connects` first. (Earlier figures in this file claimed ~235ms first audio and ~360ms complete. That was one lucky sample, and believing it is what made the bubble/voice gap look like a bug in the socket rather than the endpoint's normal spread.)
- **Newest wins, never a queue.** A second `speak` while one is in flight abandons the first, which resolves null **and does not reach the fallback either** — a slower synthesizer arriving last with the previous line is exactly the failure the supersede exists to prevent. Frames carry `X-RequestId`, so late audio for an abandoned line cannot be spliced onto the front of the next one. Same argument as the throttle in §Speech: a status line is only worth hearing while it is still true.
- **Fallback, shipped with the feature rather than after it** — `createLocalVoice({execFile, fs, tmpDir})` shells `powershell.exe` with an `-EncodedCommand` (base64 UTF-16LE) one-line `System.Speech` script that writes a WAV. Used when Edge fails **or** when `GANYU_VOICE` pins it. **`powershell.exe` (5.1), never `pwsh` 7.x**: `System.Speech` is a .NET-Framework assembly and `Add-Type -AssemblyName System.Speech` fails on 7. `-EncodedCommand` means no shell ever parses the text, which came from an LLM; inside the script it is a single-quoted PowerShell literal with its quotes doubled.

  **This machine is Windows 11 21H2 (build 22000), and that is why Edge TTS is the primary path.** The modern "natural" voices need 22H2 / build 22621 and cannot be installed here at all, so the only local voices present are the 2005-era SAPI5 ones. The fallback sounds dated on purpose — it is what she has with no network — and this file must not be "simplified" down to it.
- **Config** — `.env.local`, parsed by the same `parseEnvFile` the brain uses so the file has one format. Three keys, **none required**: `GANYU_VOICE` (**default on**; `off`/`0`/`false`/`no`/`none`/`mute` silences her, `local`/`sapi`/`offline` pins the local path and never touches the network), `GANYU_VOICE_NAME` (default `en-US-AvaMultilingualNeural`), `GANYU_VOICE_AMBIENT` (**default on**; off leaves her answering when spoken to and silent the rest of the time, which is the one half someone might reasonably not want since ambient lines arrive unprompted). No `.env.local` at all is a pet with a voice — unlike the brain, this path needs no key from him. One startup line: `voice: edge (en-US-AvaMultilingualNeural)`.

**Where it hangs, and why there is no second path.** The audio comes off **speech.mjs's existing `show()` gate** — `createSpeech({voice, onAudio, audioHoldMs, schedule, cancel})`, after mute, after salience and after the throttle. Whatever reaches the bubble is what she says, so **giving her a voice cannot make her talk more**: the salience gate, the 90s non-urgent throttle and the 6s same-kind urgent floor are unchanged and still the only things deciding when she speaks at all. Mute silences the audio with the bubble, which is the point of mute.

**The bubble waits for the voice — `AUDIO_HOLD_MS` (3.5s).** She used to show a line the instant it was decided and speak it 1.4–3.9s later, so he read the sentence, sat in silence, then heard it narrated after he had moved on. A line is now **held** until its audio is ready and the two are emitted together on `ganyu:speak`.

- **Why 3.5s.** It clears the measured p90 (3090ms) of warm-socket synthesis, so roughly nine lines in ten land voiced; 2s would expire on about half of them, which is a feature that does not work. It is **not** a latency budget — it is a floor on how long she may be silent *and* invisible. Almost nothing waits it out: a refused socket, a dead endpoint, a socket that dies mid-sentence and a voice that is switched off all resolve `speak()` to null in milliseconds and show the line immediately. The two cases it genuinely bounds are the hangs — a connect that never completes (`CONNECT_TIMEOUT_MS`, 5s) and a socket that accepts the request and never answers (`SPEAK_TIMEOUT_MS`, 10s) — which is why it sits well under both.
- **Urgent kinds are never held.** `INTERRUPT_KINDS` (`waiting`, `failed`) show synchronously and are voiced when the audio lands, on `ganyu:audio`. Holding "Claude needs your approval" for three seconds to wait on a synthesizer would trade the one thing the bubble is *for* against the polish of hearing it in sync. The accepted cost: for those two kinds the read-then-hear gap remains.
- **No voice, no wait.** Muted, `GANYU_VOICE=off`, `GANYU_VOICE_AMBIENT=off`, or module V missing — there is nothing to wait for and the line is emitted synchronously, exactly as before. A pet whose bubbles got slower the moment he silenced her would be a strange way to honour the request.
- **Deciding and showing are two moments.** Everything that makes `show()` a *decision* — the throttle, `lastSpokeAt`, `shownCount`, the recent-lines memory, the descriptor it returns — still happens synchronously; only the emit is deferred. So a held line still blocks the next one, and `awaitBrain`'s staleness check still compares against a count that moves at decision time rather than at paint time.
- **Ordering: one slot, newest wins.** `held` is a single pending utterance, not a queue. A line that decides to show cancels whatever was waiting — dropping it outright, never showing it late — so two lines cannot arrive out of order and a stale one cannot overwrite the line that displaced it. This is the same rule as the throttle and as voice.mjs's own supersede: a status line is only worth showing while it is still true, and a bubble that appears only to be replaced a moment later is worse than one that never appeared. `stats().holding` reports the slot; `dispose()` empties it.
- **Nothing is ever lost to it.** The deadline shows the line unvoiced; audio that arrives afterwards is still played on `ganyu:audio` if that line is still the current one, so a slow endpoint costs her the sync and not the voice. Mute is re-checked at release, exactly as `awaitBrain` re-checks it — but the *bubble* still appears, because swallowing it too would make muting her look like turning her off.

**Chat replies are held the same way**, through `registerIpc({onReply})` — which is **no longer fire-and-forget**: `handleChat` awaits it and resolves `{text, audio}` so the strip paints the words and plays them in one tick. The deadline lives in `speakReply` (index.mjs), where the synthesizer and the mute flag already are; `onReply` must therefore always settle, and `handleChat` treats a throw or a rejection as "no audio", never as "no answer". **The pending dots carry the wait** — the same three dots that already covered the brain writing the line now cover the synthesizer voicing it, deliberately rather than adding a second kind of waiting. A reply needs no salience gate: he asked, so it is wanted by construction.

**Playback is the renderer's**, `createVoicePlayer` in `pet.mjs` over one `<audio id="voice">` element, fed a `data:` URL. The CSP allows `media-src data:` and nothing else, so that element can never reach the network, and only `audio/mpeg` and `audio/wav` are ever pasted into a `src`. **A new line interrupts the one being spoken; it never queues** — the bubble already replaces rather than queues, and a queue would leave her voice describing the previous line while he reads this one. A missing `<audio>` element is a silent pet rather than a broken one, so it is deliberately not in `boot()`'s required-element guard.

### Wander (module E)

`createWander({clock, schedule, moveWindow, getWorkArea, getWindowSize, getPosition, onWalkState, isPinned})` — all side effects injected; `schedule(fn, ms)` returns a cancel handle (production: setTimeout).

- `getWindowSize()` → `{width, height}`: the **measured** outer size of the window, read on every `bounds()` call. Falls back to the `windowWidth`/`windowHeight` defaults (256×320) when absent or when it returns garbage, so unit tests need not inject it. See §Window for why module A measures once and caches rather than reading `getBounds()` live.
- `getPosition()` → `{x, y}`: where the window really is, drags included. This is what makes containment possible at all — without it the module only knows the position it last set. Ignored while she is strolling or falling, because mid-motion the module owns the position and re-reading a rounded value each tick would fight the float integration.

- **Calm modes** (`WANDER_DEFAULTS`-adjacent export `CALM_MODES = ['idle', 'busy']`, plus an `isCalm(mode)` helper): she strolls while the aggregate mode is `idle` **or** `busy`. `busy` counts as calm because the owner always has codex/Claude Code sessions open, so the lifecycle-hook stream pins the aggregate at `busy` indefinitely and `idle` effectively never arrives — gating on `idle` alone meant she never walked at all, just looped the non-directional busy run on the spot.
- Arms **20s** after entering a calm mode from a non-calm one. Then every **45–120s** (deterministic from injected `random`): pick target x in work area, walk at ~60 px/s (move window every 50ms tick), face travel direction (`onWalkState({dir})`), occasional mid-walk pause (idle 3–8s).
- A transition **between** two calm modes (idle↔busy, which the hook stream does constantly as sessions start and stop) neither interrupts a stroll in progress nor restarts the countdown. Only a **non-calm** mode (`waiting`, `failed`, or any unrecognized mode) → instant cancel, `onWalkState(null)`. Repeated identical modes are ignored. Pinned → never arms.
- **Edge bounce.** Targets are always picked inside the work area, but a wall can move under her mid-stroll (the work area shrinks, a monitor is undocked). When the next step would cross `minX`/`maxX` she stops at the wall, picks a fresh target back the other way, and flips the direction reported through `onWalkState` — she turns around rather than stopping dead against the edge. Arrival still wins over the wall check, so a target sitting exactly on an edge ends the stroll normally.
- Renderer precedence follows from this: `walk.dir` outranks the mode row, so a stroll under `busy` draws the directional run rows (1/2), not the stationary busy row 8.

**Containment — `containNow()`.** Re-clamps the window into the current work area from wherever it is, then hands off to gravity if it is above the floor. Callable at any time from any state: **no mode check, no pinned check, no stroll required**, and a no-op (not one `moveWindow` call) when she is already fully inside. Returns true if it moved her. This is the fix for the owner losing the pet off-screen: `syncPosition()` alone only re-clamped at the *start* of a stroll, so a work-area change or a drag left her outside with nothing to pull her back — and with the aggregate mode stuck non-calm (`waiting`/`failed`) wander is cancelled and no stroll ever comes, so she stayed lost indefinitely. **Pinned does not exempt containment**: a pinned pet stranded off-screen was exactly the trap. Module A's call sites are in §Window.

**Physics.** `WANDER_DEFAULTS` adds `gravityPxPerSec2: 1400`, `maxFallPxPerSec: 900`, `restitution: 0.25`, `minBounceVelocity: 120`.

- **Floor** = work area bottom minus the **measured** window height. Y is no longer a constant: it changes while she falls, and `moveWindow` receives the updated y. The renderer is unaffected — it draws in-window.
- Whenever she is above the floor — dragged up, or left high by a display change — she **falls**: `vy += gravity·dt`, `y += vy·dt`, capped at `maxFallPxPerSec`, on the existing `tickMs` cadence with the same `maxTickDtMs` clamp so a suspended timer cannot teleport her. On reaching the floor she bounces with `restitution`, and once the rebound is below `minBounceVelocity` she settles **exactly** on the floor. With these constants that is one or two bounces.
- **Falling outranks strolling**: it cancels a stroll in progress (`onWalkState(null)`), then normal scheduling resumes on landing. It also outranks the mode and the pinned flag — gravity is containment, not behaviour, so it runs while pinned and while the mode is non-calm. Only `stop()` (teardown) cancels a fall; `cancel()` and a non-calm `setMode` deliberately leave it running rather than leaving her hanging in mid-air.
- Diagnostics: `isFalling()` and `isHeld()` alongside `isWandering()` / `isArmed()`. Neither falling nor being held is "armed" or "wandering".

**Being held — `grab()` / `moveTo(x, y)` / `release({vx, vy})`.** The drag lives here rather than in module A because there must be exactly one writer of the window position; module A owns the *input* (§Drag) and this owns where she ends up.

- `grab()` suspends the module the same way a non-calm mode does — arm timer cancelled, stroll abandoned, fall dropped — and adopts the window's real position before module A starts aiming it. It ignores the pinned flag and the mode: neither is a reason he cannot pick her up.
- `moveTo(x, y)` clamps to the work area and moves her. She therefore **cannot be dragged off-screen** — containment is not something holding her should switch off — and a garbage coordinate keeps the axis it cannot replace rather than moving the window to `NaN`.
- `release({vx, vy})` hands the cursor's velocity to the physics below, clamped to `maxThrowPxPerSec` (**2400**). Already on the floor, not moving up, and under `minSlideVelocity` sideways means she was set down rather than thrown: no flight is simulated at all, and the ordinary scheduler resumes immediately.
- While held, `containNow()` is a no-op and `maybeFall` never fires — the drag is already clamping every pixel to the same bounds, and a second writer is the failure being avoided. `cancel()` leaves a held pet held, on the same reasoning that leaves a fall running; **only `stop()` ends a drag**, and it ends it by putting her down.
- `onAirborne(bool)` is the fifth callback, edge-triggered like `onWalkState`: true on `grab` or on the start of any fall, false when she settles. Module A forwards it as `airborne` on `ganyu:state` for the sprite row (§Renderer). It has to travel on the edge rather than wait for the 1s state poll, because a whole throw is over inside a second.

**Throw physics** adds `wallRestitution: 0.5`, `groundFrictionPxPerSec2: 1600`, `minSlideVelocity: 40`, `maxThrowPxPerSec: 2400`, and a horizontal `vx` that is zero for every fall that is not a throw — so an ordinary fall is still exactly vertical.

- **Walls return more than the floor does** (0.5 against 0.25) on purpose: at the floor's restitution a thrown pet hits the side of the screen and stops dead, which reads as a collision bug rather than as a bounce.
- **Landing with sideways speed is a skid, not a stop.** Friction is applied only on a tick that *began* in contact with the floor, so a flight keeps its speed and a landing spends it — and the flight does not end until `vx` reaches zero, even though `vy` already has. Without this, a flick along the floor (where there is no air time to spend the speed in) lands on the settle branch and does nothing at all, which reads as the throw having been ignored rather than as physics.

### Hook delivery (module F)

`hooks/ganyu-hook.cmd %1=source [%2=port]` — mirrors Orca's proven pattern: pipe stdin to `%SystemRoot%\System32\curl.exe -sS -X POST http://127.0.0.1:47821/event/%1 --connect-timeout 0.5 --max-time 1.5 -H "Content-Type: application/json" --data-binary @- >nul 2>&1`, then `exit /b 0` **always** — a dead pet must never block or slow an agent. If curl is missing/fails, drain stdin (`more.com >nul`) and still exit 0.

`hooks/install-hooks.mjs`:
- Targets: `~/.codex/hooks.json` (events: SessionStart, UserPromptSubmit, Stop, PreToolUse, PostToolUse, PermissionRequest, SubagentStart, SubagentStop — same envelope shape as the existing entries in that file) and `~/.claude/settings.json` `hooks` key (events: SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Notification, Stop, SubagentStop, SessionEnd; PreToolUse/PostToolUse get `"matcher": "*"`).
- **Append-only merge**: never remove or reorder existing entries (Orca + Superset hooks live there). Skip any event where our exact command already exists (idempotent). Write `<file>.bak-ganyu-N` backup first. Round-trip parse the result before writing; abort on any parse failure.
- Default is dry-run printing a unified-diff-style preview. `--apply` writes. `--codex-file <path> --claude-file <path>` override targets (used by tests against fixtures in `hooks/fixtures/`).


#### OpenCode

Verified against **OpenCode 1.18.26** (`opencode --version`, 2026-11-10) — the event and hook names were read out of the installed binary, which wins over the docs where they differ — and the plugin docs at <https://opencode.ai/docs/plugins/>.

OpenCode has no stdin hook commands; its extension point is a JS plugin. `hooks/opencode/ganyu.js` is that plugin. It exports exactly one function, `GanyuPlugin` (OpenCode 1.18 calls every exported function as a plugin), and POSTs to `http://127.0.0.1:<port>/event/opencode`, port = `GANYU_PORT` else 47821 — the same rule as `ganyu-hook.cmd`.

| OpenCode signal | `hook_event_name` sent | Mode |
|---|---|---|
| hook `tool.execute.before` | `PreToolUse` (+ `tool_name`) | busy |
| event `message.part.updated`, tool part `completed` or `error` | `PostToolUse` (+ `tool_name`) | busy |
| hook `chat.message` | `UserPromptSubmit` | busy |
| event `session.created` | `SessionStart` | busy |
| event `permission.asked` (+ `tool_name` = the permission), `question.asked` | `PermissionRequest` | waiting |
| event `permission.replied`, `question.replied`, `question.rejected` | `PostToolUse` | busy |
| event `session.idle` | `Stop` | idle + celebrate |
| event `session.error` (except `MessageAbortedError`, which is the owner pressing abort) | `Stop` + `error: <error.name>` | failed (sticky 30s), no celebrate |
| event `session.deleted` | `SessionEnd` | idle |

Known edges: an abort (`MessageAbortedError`) posts nothing, so the `session.idle` that follows it is an ordinary `Stop` and she celebrates. A subagent's `session.deleted` posts nothing, so it never ends the root session. A subagent's `session.error` arrives as `SubagentStop` + `error` and still flags the root `failed`. A finished tool part is reported once per `callID`, so a late re-publish cannot turn an idle session back to busy.

Everything else (`session.status`, `message.updated`, text parts, …) posts nothing. `session.status` is deliberately ignored because OpenCode publishes it immediately before `session.idle`, and handling both would celebrate twice. The `permission.ask` hook has no call site in 1.18.26, so the `permission.asked` event is used instead. `tool.execute.after` fires only on success, so tool-end comes from `message.part.updated`. A subagent session (`info.parentID` set) reports under its root session's id, with `SessionStart`→`SubagentStart` and `Stop`→`SubagentStop`, so a finishing subagent keeps the pet busy rather than celebrating.

**Body — the complete field list:** `hook_event_name`, `session_id` (OpenCode's `ses_…` id; sessions are keyed `source::sessionId` in state, so no prefix is needed to avoid colliding with codex/Claude), `tool_name` (optional), `cwd` (the plugin context's `directory`), `error` (`session.error` only: the error's `name`, e.g. `APIError`). Every string except `cwd` must be a short identifier (`[\w.:\-/ ]`, ≤128 chars) or it is dropped. **Never sent:** prompt or message text, tool arguments, tool output, titles, permission patterns or metadata, error messages, file contents.

**Never blocks OpenCode:** nothing is awaited — the `event` hook is not awaited by OpenCode, but `tool.execute.before` and `chat.message` are, so those return synchronously; each POST is fire-and-forget with a 1s `AbortSignal.timeout`; every throw and rejection is swallowed and nothing is printed.

**Install:** `node hooks/install-hooks.mjs --opencode` (opt-in; `--opencode-dir <dir>` overrides the dir and implies it). OpenCode 1.18 loads `{plugin,plugins}/*.{js,ts}` from its global config dir, `$XDG_CONFIG_HOME/opencode` else `<home>/.config/opencode` — on Windows too, there is no `%APPDATA%` branch. The target is `<config dir>/plugins/ganyu.js`, planned through the same `planTarget` → `validatePlan` → `unifiedDiff` → apply path as the JSON targets, as a whole-file copy: dry run by default; `--apply` backs a differing `ganyu.js` up to `ganyu.js.bak-ganyu-N` (a name OpenCode's glob does not load) before replacing it; a second `--apply` changes nothing; no other plugin is opened. A missing config dir, a config dir that is a file, a `plugins` that is a file, or a `ganyu.js` that is a directory throws before anything is written.
